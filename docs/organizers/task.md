# CQA — задание для участников хакатона

> Источник: `CQA_Hackathon_Student_Guide_v3 1.pdf` (Freedom Broker / CQA Hackathon). Текстовая версия для репозитория.

## 01 / Задача — Оценка качества диалогов

Разработайте прототип **Conversation Quality Analytics** за 24 часа.

### Что должна уметь система

1. **Настройка и автоматическая оценка.** Пользователь настраивает чек-лист, загружает диалоги и запускает оценку работы оператора. Система показывает баллы, объяснения и реплики, на которых основан вывод.
2. **Результаты, апелляция и пересмотр.** Пользователь просматривает оценку и оспаривает критерий. Проверяющий изучает доказательства, подтверждает или меняет оценку и сохраняет финальный результат.

### Данные и материалы

- **DEV для разработки.** 65 диалогов: 60 синтетических чатов и 5 реальных звонков. Языки набора: 35 RU, 15 KZ и 15 EN. Для звонков доступны транскрипт и ссылка на запись.
- **Чек-лист.** Отдельный PDF с восемью критериями, весами, шкалами и правилами N/A. Используйте его как начальную конфигурацию (см. [checklist.md](checklist.md)).
- **API организаторов.** GET возвращает набор по `group_id`. Подключение и формат ответа — в разделе 03.
- **Контроль.** Через 23 часа после старта организаторы откроют дополнительные транскрипты. На отдельной проверке организаторы предложат заменить один критерий. Сохраните новый чек-лист через интерфейс и примените его к выданным диалогам.

### Формат решения

- **Интерфейс** на HTML, CSS и JavaScript. Продумайте структуру так, чтобы интерфейс можно было в дальнейшем адаптировать как HTML-компонент Dynamics 365.
- **Сервис оценки и данные.** Модель, серверную часть и способ хранения команда выбирает самостоятельно. Для демонстрации регистрация и вход в систему не нужны.

## 02 / Функции — Что реализовать

### Контур 1 · Оценка

1. **Создайте чек-лист.** Добавляйте и меняйте критерии, формулировки, вес, тип ответа и доступность N/A. Для числового критерия задайте шкалу. Новый критерий должен применяться через настройки. Сохраните конфигурацию оценки.
2. **Оцените выбранный диалог.** Загрузите транскрипт, выберите чек-лист и запустите оценку оператора. Поддержите RU, KZ и EN. Реплики бота и системные события служат контекстом.
3. **Покажите результат.** Для каждого критерия покажите ответ, баллы, вес, объяснение и реплику-доказательство. Если действие пропущено, укажите проверенный участок разговора. При N/A объясните причину. Покажите итог и результаты секций, если они заданы.

> **Вес и итог.** Пересчитывайте шкальные оценки с учётом веса. При N/A перераспределяйте вес между применимыми критериями. Грубая ошибка отмечается отдельно. Применяйте правила и округление из выданного чек-листа.

### Контур 2 · Работа с результатом

4. **Откройте карточку.** Из списка перейдите к транскрипту и результату. Ссылка в обосновании должна приводить к нужному сообщению или фрагменту звонка. Для записи предусмотрите прослушивание или переход к плееру.
5. **Подайте апелляцию.** Выберите критерий, добавьте комментарий и сохраните обращение. Проверяющий видит спорную оценку, комментарий и фрагмент диалога.
6. **Примите решение.** Проверяющий подтверждает или меняет оценку и указывает причину. Система пересчитывает итог. В карточке доступны исходная оценка, решение и финальный результат.

## 03 / Данные — Временный API

Получите набор запросом **GET** с параметром `group_id`. Для контрольного набора организаторы сообщат другое значение `group_id`. URL эндпоинта хранится в `.env` (см. [../data/README.md](../../data/README.md)).

```bash
curl "<URL эндпоинта>&group_id=DEV"
```

### Формат ответа

```json
{ "error": "", "isSuccess": true, "data": {
    "dataset_group_id": "DEV", "total_records": 65,
    "records": [{
      "conversation_id": "p1-ru-001",
      "channel": "agent chat", "language": "RU",
      "transcript": [{"timestamp": "00:02", "speaker": "operator", "text": "Здравствуйте!"}],
      "audio_url": null
    }]
} }
```

- **Данные.** При успехе `isSuccess = true`, а `data.records` содержит записи. `conversation_id` — ID диалога, `channel` — `agent chat` или `voice call`, `language` — `RU`, `KZ` или `EN`.
- **Транскрипт.** Поле `transcript` уже является массивом. У реплики есть `timestamp`, `speaker` и `text`. Роли: `client`, `operator`, `bot`, `system`. Сохраняйте исходные метки времени.
- **Время и звук.** У чатов время задано как `MM:SS`, у звонков — ISO 8601 с часовым поясом. `audio_url` пустой у чатов и содержит ссылку у звонков.

## 04 / Сдача — Защита за 5 минут

### Тайминг

- **+23 ч.** Организаторы открывают контрольные транскрипты. Запустите их обработку заранее, чтобы результаты были готовы к выступлению.
- **+24 ч.** Стоп-код. Зафиксируйте последний коммит. Жюри проверит эту версию. Обработку данных и изменение чек-листа через интерфейс можно выполнять на зафиксированной версии.

> **До стоп-кода.** Закоммитьте решение в открытый Git-репозиторий и заранее отправьте ссылку организаторам. Добавьте README с понятными шагами запуска.

### План презентации (максимум 5 минут)

| Время | Что показать |
|---|---|
| 1 мин | Интерфейс и выбранный диалог |
| 2 мин | Оценка, обоснование и переход к реплике. Пример N/A и итоговый балл |
| 1 мин | Оспорить оценку, решение проверяющего и новый итог |
| 1 мин | Изменение критерия и применение чек-листа |

### Частые вопросы

- **Какой ИИ использовать?** Локальную модель, бесплатный или платный API. Для платной модели укажите название и примерную стоимость одной оценки с учётом всех её вызовов.
- **Нужно ли распознавать речь?** Транскрипты уже выданы. Для оценки дикции и интонации нужен звук.
- **Что делать при ошибке CORS?** Запрашивайте данные через серверную часть или локальный адаптер.
- **Нужна ли авторизация?** Нет. Подачу апелляции и её проверку покажите как отдельные действия в интерфейсе.
