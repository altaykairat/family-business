# Задание для сессии Claude Code: реализация платформы

## Кто ты в проекте

Ты — сессия **реализации платформы**. Параллельно работают:
- **сессия дизайна** (Claude Code) — решает, *как* должен быть устроен пайплайн: обсуждения, решения, каталог параметров, протокол экспериментов, шаблоны промптов;
- **Antigravity и Codex** — строят альтернативные прототипы пайплайна в `variants/`.

Твоя задача — превратить базу в **платформу**: надёжное ядро, хранилище, историю, версии, контур апелляций и обучения, точку подключения для будущего фронтенда. Ты разрабатываешь систему, а **не выполняешь её LLM-шаги**: промпты прогонов человек сам отправляет в новые чаты облачных моделей и вставляет ответы обратно. LLM в рантайме сейчас нет — ни API, ни локальной модели.

## Проект в двух абзацах

**CQA (Conversation Quality Analytics)** — прототип для хакатона Freedom Broker: система оценивает работу операторов контакт-центра (чаты RU / KZ / EN и звонки) по чек-листу организаторов из 8 критериев — с ответами по критериям, баллами, объяснениями и цитатами-доказательствами. Дальше — апелляции, решения проверяющих (решение человека — абсолютная правда), история всех событий и цикл обучения системы на решениях.

Главный критерий отбора — **точность** на 10 скрытых диалогах относительно эталона экспертов (вероятно, сравнивают итоговый балл и суждения: аргументы и цитаты). Второй — глубина цикла обучения и аналитики. На защите жюри попросит заменить критерий через интерфейс и применить новый чек-лист.

## Что строить

Направление — по решениям команды; **как именно — решай сам**, включая стек, хранилище и структуру кода. Ниже — что нужно платформе, примерно в порядке ценности:

1. **Эталон и метрики точности (S9).** Формат разметки эталона, импорт, расчёт метрик (точность по критериям, путаница «Нет» ↔ N/A, ошибка итогового балла, валидность и совпадение доказательств, стабильность, стоимость), отложенная тестовая часть, сравнение прогонов и вариантов лоб в лоб — включая варианты Antigravity и Codex.
2. **Хранилище и история (решения 8, 10).** Журнал событий только с добавлением; факты и измерения, чтобы любую связь можно было посчитать одним запросом; импорт результатов прогонов.
3. **Version control (решение 9).** Версии чек-листа, шаблонов промптов, параметров, признаков, модели; каждая оценка ссылается на полный набор версий; diff; «машина времени»; архив вместо удаления.
4. **Контур апелляций (решения 4, 7).** Апелляция на критерий → решение проверяющего (подтвердить / изменить, причина, тип A–D) → итоговая оценка вычисляется поверх исходной, исходная не меняется; прецеденты по кнопке; люди с id (решение 20).
5. **Цикл обучения (S10).** Выжимка из истории — алгоритмом; предложения оркестратора хранятся и применяются только человеком; регрессионный прогон перед активацией версии. LLM-шаги оркестратора — тоже файлы промптов / ответов для ручной обработки.
6. **Аналитика по людям и связям** — статистика операторов, проверяющих, пар, критериев (с размером выборки, без автоматических ярлыков).
7. **Точка подключения фронтенда.** Каждое действие из таблицы MC — команда и вызов API, чтобы фронтенд можно было подключить без переделки ядра. Сам фронтенд не делай: у владельца проекта свои идеи по интерфейсу. Задание требует, чтобы интерфейс можно было адаптировать как HTML-компонент Dynamics 365 — учти это в контракте API.
8. **Провайдеры LLM.** Абстракция провайдера: сейчас — файловый (ручной) режим, позже — CLI / API / локальная модель без переделки пайплайна.

Соответствие наших id критериев кодам `contact … critical` — в профиле экспорта в конфиге (не в коде и не в `default/v1.json`). Перевод `yes/no/na/число` → `true/false/null/число`; `rationale` из `explanation`; `evidence_turns` из проверенных доказательств (наш 1-based `idx` совпадает с их нумерацией); `final_score` и `critical_flag` из S7; ошибки → `status: "error"`, `criteria: []`, `score: null`, причина. Команда проверки файла перед push: 8 критериев ровно по разу, типы значений, уникальные ID, ожидаемое число записей, UTF-8. Экспорт по чек-листу без полного соответствия кодам — понятная ошибка.
- **0b. Четыре сценария жюри — приёмочные тесты** (через API, фронтенд не делаешь): список диалогов с грубыми ошибками и объяснениями; апелляция, которую инициирует **оператор**; добавить / изменить критерий и вес → новая версия → пересчёт и экспорт; результат диалога с обоснованием и доказательствами.
- **0c. Автоматический провайдер.** К демо понадобится хотя бы один провайдер без ручной вставки (выбор — открытый вопрос Q18). Абстракция из пункта 8 должна позволять подключить его конфигом; ручной режим остаётся.

## Рамки

- Решения команды обязательны; материалы организаторов не меняются.
- Только чек-лист организаторов; ни одного критерия в коде.
- Баллы — формула, не LLM; существующие тесты `tests/` не ломать, новое — с тестами.
- Ничего автоматического без кнопки (решение 11): автоматические режимы — только как выключенные опции.
- Совместимость с прогонами V1 (`runs/r001`) и с форматом результата, который используют варианты (`runs/<run>/validated/<agent>/<id>.json`).
- Зона: `cqa/`, `scripts/`, `tests/`, `config/`, `docs/team/pipeline.md`, новый `docs/team/implementation.md`. Шаблоны промптов и документы дизайна — зона сессии дизайна: нужные изменения предлагай в своём документе. Правила общего каталога — `docs/team/agent-briefs/README.md`.
