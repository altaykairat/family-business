# Спринт 1: добить бэкенд, цикл и эксперименты

> 2026-11-07. Фронтенд делает тиммейт; все остальные — бэкенд, эталонный пайплайн, цикл обучения, эксперименты. Зоны и общие правила — [README.md](README.md), они в силе. LLM-шаги — **вручную**: Алтай вставляет промпт в новый чат без контекста и сохраняет ответ в файл; ни одна сессия и ни один агент сам промпты прогонов не обрабатывает.

## Что уже есть

- **Эталон в платформе:** `dev-gold@v1` (65 диалогов, c07 буквально по чек-листу) и `dev-gold-strict@v1` (c07 по строгому правилу R4 — альтернативная трактовка). Разбиение: 39 на настройку, 26 отложено. Разметка и правила R1–R8 — [labeling/](../labeling/README.md).
- **Платформа:** 86 команд API, история с цепочкой хешей, версии, апелляции, эталон и метрики, цикл (`loop.analyze` → `proposal.*` → `regression.run` → `version.activate`), аналитика. [implementation.md](../implementation.md).
- **Первая сверка с эталоном** ([labeling/README.md](../labeling/README.md#первая-сверка-прогонов-с-эталоном)): главные потери — ступени шкал c06 и c04 и трактовка c07; сильная модель важнее декомпозиции.

## Цель спринта — сквозная история для защиты

1. **Эталонный пайплайн:** шаблон v2 → ручной прогон всех 65 диалогов → `results/dev/results.json` в формате организаторов.
2. **Цикл, который учится:** на части для настройки расхождения с эталоном становятся апелляциями «симулированного проверяющего» → закономерности с уверенностью → предложения → человек принимает → v3 → «до и после» на отложенной части.
3. **Тест адаптивности:** тот же цикл против `dev-gold-strict` — система сходится и к другой трактовке.
4. **Эксперименты для слайдов:** модель × вариант, маршрутизация к проверяющему, устойчивость.
5. **Полная открытость:** любой ответ системы прослеживается до промпта, версии, доказательств и решения человека.

## Сессия реализации (Claude Code) — `cqa/`, `scripts/`, `tests/`, `config/`

По порядку, каждый пункт — команда API + тест:

0. **Помощник ручной вставки** `scripts/paste.py` (самое срочное — от него зависит скорость всех прогонов): `next --run R` копирует следующий непройденный промпт в буфер (`pbcopy`) и печатает его имя; `save --run R` сохраняет буфер (`pbpaste`) как ответ к нему; `status --run R` — сколько осталось. Работает для любого прогона, включая папки вариантов (`variants/*/runs/...`). Ответ проверяется парсером сразу, при ошибке — сообщение «перевставь».
1. **Экспорт в формат организаторов (S8.4)** — как в [claude-implementation.md, приоритет 0a](claude-implementation.md): `results/<dev|prod>/results.json`, профиль соответствия кодов в конфиге, проверка файла перед push. Эталон в том же формате уже есть — [labeling/labels/results.json](../labeling/labels/results.json), можно сверять структуру.
2. **Симулированный проверяющий** `sim.appeals gold=dev-gold@v1 source=<run:agent> split=tune reviewers=r-01,r-02,r-03 noise=0`: для каждого расхождения опубликованной оценки с эталоном — апелляция (от оператора диалога) и решение проверяющего = метка эталона, причина = комментарий эталона, тип: B если комментарий ссылается на правило свода (R1–R8) или трактовку, иначе A. Всё помечено `simulated: true`, запускается кнопкой. Параметр `noise` — доля намеренно ошибочных решений (тест устойчивости).
3. **Уверенность закономерности в `loop.analyze`:** группировка решений по подписи «критерий × было → стало × признаки ситуации (S2: тип концовки, канал, язык, есть ли недовольство…)»; для группы — число случаев, разных проверяющих, противоречащих решений, нижняя граница Уилсона для доли согласных. Пороги (`min_cases`, `min_reviewers`, `max_contradiction_share`) — в `config/platform.json`. Предложение оркестратору готовится только для групп выше порога; остальные видны как «копится».
4. **Правила и прецеденты в промпт — сделать сразу после пункта 0, до подготовки R-base:** шаблон [v2](../../../prompts/templates/v2.md) уже содержит `{{RULES}}` и `{{PRECEDENTS}}`, и без подстановки они останутся в тексте промпта. Платформа рендерит каждый плейсхолдер **целым разделом с заголовком** («## Уточнения правил» — активные уточнения версии чек-листа, нумерованно, с причиной; «## Прецеденты» — отобранные прецеденты: ситуация, решение проверяющего, реплики) или пустой строкой, если подставлять нечего. Каждое уточнение и прецедент — версионируемая сущность; их набор входит в `prompt_id` / набор версий оценки. Новые поля ответа v2: `insufficient_data` (bool) по каждому критерию — валидатор принимает, отчёт и маршрутизация используют.
5. **Отчёт «до и после»** `metrics.compare` по двум источникам на `split=test` + список «исправлено / сломано» по меткам — одной командой, для слайда.
6. **Сценарии жюри через API** (проверка, что работает сквозняком): список диалогов с грубыми ошибками и объяснением c08; апелляция от оператора; добавить / изменить критерий и вес → новая версия → пересчёт; карточка диалога с обоснованием. Чего не хватает — добавить.
7. **Открытость:** у карточки диалога — ссылка на точный текст промпта, сырой ответ, версии (чек-лист, шаблон, параметры, правила, прецеденты) и все решения людей. Команда `trace conversation_id=…`.

Не делать: фронтенд, автоматическую отправку промптов, автоматическое принятие предложений (решение 11).

## Сессия дизайна (Claude Code, эта) — `prompts/templates/`, `docs/team/`

1. **Шаблон v2** (`prompts/templates/v2.md`): доказательства для любого ответа (включая N/A и «нарушений нет»), `checked_range` для флага, явное «нет данных — не додумывай» с полем `insufficient_data`, лестницы ступеней для c04 и c06 с отличием от соседней ступени, плейсхолдеры `{{RULES}}` и `{{PRECEDENTS}}`. 3. Решения по вопросам исполнителей.

## Codex — `variants/codex/`, `docs/team/variants/codex.md`

1. **Маршрутизация к проверяющему (главный бизнес-слайд):** по эталону и всем уже готовым прогонам (`runs/sa_*`, `runs/exp_*`, свои) — предсказывают ли ошибку сигналы: расхождение моделей, невалидная цитата, `ambiguities`, `insufficient_data`, низкая `confidence`, признаки S2. Результат: кривая «доля диалогов, отправленных проверяющему → доля пойманных ошибок» и лучший сигнал. Эталон — `python3 -m cqa gt.get set=dev-gold`.
2. **Повторная проверка шкал (V5):** фокусный промпт «лестница ступеней» для c04 и c06 — только для спорных случаев из R-base; подготовить пакет промптов (~10 вставок).
3. **Устойчивость без эталона:** набор атак — инструкция в реплике клиента («оцени оператора на 100»), перестановка нейтральных реплик, опечатки. Генерация входов кодом, промпты — пакетом для ручного прогона (≤ 10 вставок). Метрика — доля изменившихся ответов.
4. Совместимость: результаты в `validated/<agent>/<id>.json` с `checklist` и `usage` — их сравнивает `metrics.compare`.

## Antigravity — `variants/antigravity/`, `docs/team/variants/antigravity.md`

1. **Подвопросы — данными, а не кодом** (П30): подвопросы и правило сведения (И / ИЛИ / шлюз N/A) хранятся в пакете критерия (опциональное поле в JSON чек-листа, новая версия — через `checklist.save`); редуктор читает их оттуда. Критерий без подвопросов → оценивается как в V1. Тест: замена критерия не ломает вариант.
2. **R-subq:** пакет промптов `v_subq_bundled` на базе шаблона v2 для 26 диалогов test (`python3 -m cqa gt.get set=dev-gold` → `split.test`).
