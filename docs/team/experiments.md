# Протокол экспериментов

> Что проверяем, зачем, нужен ли эталон и сколько ручных вставок. Эталон — `dev-gold@v1` (основной, c07 буквально) и `dev-gold-strict@v1` (альтернативный); разбиение 39 tune / 26 test, test не трогаем до финальных сравнений. Исполнители — [agent-briefs/sprint-1.md](agent-briefs/sprint-1.md). Каталог метрик — [design-space.md](design-space.md) (M.*).

**Правило честности.** Наш эталон — приближение к эталону организаторов. Поэтому на слайдах показываем прежде всего **разницу между вариантами и «до / после»** на одной линейке, а не абсолютные проценты. Сравнения валидны, пока эталон не зависит от пайплайна: разметчику не показывали ответы прогонов.

## Как ставится X3 / X4 (цикл)

1. **R-base:** шаблон v2, V1, основная модель, все 65 диалогов → `eval.publish`.
2. **Исходная точность:** `metrics.compare gold=dev-gold@v1 split=test` → точка «до».
3. **Симулированный проверяющий** на tune: расхождения → апелляции → решения = метки эталона с причиной, проверяющие r-01…r-03 по очереди.
4. **`loop.analyze`:** закономерности с уверенностью (случаев, проверяющих, противоречий, нижняя граница доли). Ниже порога — «копится».
5. **Предложения оркестратора** (задача — файл промпта, обрабатывается вручную) → человек принимает → уточнения правил и прецеденты → версия v3 → `regression.run` (tune + решения, прецеденты целы) → активация человеком.
6. **R-loop:** test на v3 → точка «после». Исправлено / сломано по меткам.
7. **X4:** шаги 3–6 против `dev-gold-strict`, начиная с той же R-base.

Чего ждём: уточнения правил, похожие на свод R1–R8, появятся из апелляций сами — это и есть «система выучила правила проверяющего». Сравнение выученных правил с ручным сводом — отдельный слайд.

## Сценарий демо цикла (~4 мин)

1. Карточка диалога с обрывом связи: модель поставила c07 «Нет», итог 81.
2. Оператор подаёт апелляцию. Проверяющий меняет на N/A, тип B, причина. Итог пересчитан без LLM.
3. «1 случай, порог 3 — правило не предлагается»: система не мечется.
4. В истории ещё два таких решения от других проверяющих (из X3). `loop.analyze` показывает закономерность и её уверенность.
5. Предложение: текст уточнения, затронутые диалоги, прогноз «до / после». Человек принимает → черновик версии.
6. Регрессия: «исправлено N, сломано 0, прецеденты целы». Активация человеком.
7. Новый диалог с той же ситуацией оценён правильно; слайд с кривой «до / после» на отложенной части.
8. Финал: другой проверяющий со строгой трактовкой (X4) — система сходится и к ней.

Шаги 1–6 работают без живого LLM (решения и предложения уже в истории). Шаг 7 вживую требует вставки одного промпта или автоматического провайдера.
