# Codex: проверка, маршрутизация, гибрид

Реализованы три файловых прототипа в `variants/codex/`; общий код и материалы организаторов не изменены. Разработчик не выполнял LLM-шаги. Есть подготовленные промпты, структурные признаки всех 65 DEV-диалогов и тесты. Доказательств прироста точности пока нет: ответы моделей и человеческий эталон отсутствуют.

## Запуск

Из корня репозитория, Python 3.9+, без обязательных зависимостей:

```bash
python3 -m unittest discover -s variants/codex/tests -v
python3 -m variants.codex prepare --run variants/codex/runs/my-review --variant review
python3 -m variants.codex ingest --run variants/codex/runs/my-review
python3 -m variants.codex route --run variants/codex/runs/my-review
python3 -m variants.codex ingest --run variants/codex/runs/my-review
python3 -m variants.codex report --run variants/codex/runs/my-review
```

`prepare` без `--ids` готовит весь DEV. Опции: `--ids ID ...`, `--dataset dev`, `--checklist default@1`, `--config variants/codex/config.json`. Для других вариантов: `--variant sections` или `--variant hints`; `route` им не нужен.

Ручной шаг между командами: каждый файл `agents/<agent>/prompts/*.md` отправить целиком в новый независимый чат соответствующей модели; ответ сохранить как `agents/<agent>/responses/<то же имя>.json` (также поддерживаются .md/.txt). Изначально одинаковые промпты подготовлены для claude, codex, antigravity. Модель и её фактическую версию записать в ответе/usage, название папки не является названием модели. Не запускать разработчика для обработки этих промптов.

Для review после первого ingest нужны исходные ответы **всех** моделей. Команда route запускается человеком, фиксирует объединённый набор спорных критериев и выдаёт каждому агенту одинаковый независимый промпт `__review.md`. Предыдущие ответы и причины отбора скрыты от повторного оценщика, чтобы уменьшить якорение. Затем человек переносит ответы повторной проверки и ещё раз запускает ingest/report. Маршрут не перезаписывается; другая политика — новый прогон.

Подготовленная общая выборка: p1-ru-001, p1-ru-012, p1-ru-022, p1-ru-029, p1-kz-001, p1-kz-008, p1-en-015, p4-ru-001. Это намеренно выбранный диагностический пилот, а не случайный hold-out. Каталоги `variants/codex/runs/pilot-*-v2/` — текущие подготовленные прогоны; v1 сохранены как предыдущая подготовка. Ни в одном нет реальных ответов моделей. Результаты правил на полном DEV: `variants/codex/artifacts/dev-features/`.

## Схемы: этап × исполнитель

Общее: S0 — снимок чек-листа и параметров; S1 — нормализация ядром; S2 — алгоритм; S3 — шаблон V1 из версии чек-листа; S4 — человек переносит промпт и ответ облачной модели; S5 — парсер и строгая проверка; S7 — `cqa/scoring.py`; S8–S9 — отчёт затрат и согласия, точность только после человеческой разметки; S10 — локальный журнал событий и снимки результатов.

| Вариант | S2–S4 | S5–S6 | Вызовов на диалог на модель |
|---|---|---|---|
| sections / V2 | полный диалог и общие правила в каждом запросе, критерии сгруппированы по секциям текущей версии | проверка частей и объединение по id | число непустых секций, сейчас 4 |
| review / V5 | исходный V1, затем один пакет только спорных критериев | общий маршрут по всем моделям; независимая перепроверка; предложение человеку | 1 или 2; среднее 1+r |
| hints / гибрид | V1 + словарные совпадения с точными idx и исходным текстом | те же строгие проверки; подсказки не заменяют ответы | 1 |

Жюри доступно всем вариантам в report: строгое большинство исходных ответов по критерию, число голосов, доля согласия и исходные голоса. При ничьей или недостаточном числе голосов для большинства всей панели — `proposal: null`. Это предложение, не ground truth. Объяснения не склеиваются из разных моделей: оригиналы доступны в validated. Повторная проверка хранится отдельно в `review_proposal`; она **не перезаписывает** исходные ответы или оценку. Человеческие решения не импортируются и не изменяются этим прототипом: их владелец — общий контур платформы.

## Маршрутизация и правила

В конфигурации: порог паузы, словари, флаги маршрутизации, порог самооценки уверенности, модели/цены и сценарии доли повторных проверок. Ни одного c01…c08 в логике прототипа нет. Триггеры review:

- пропущенный/недопустимый ответ, ошибка проверки доказательств;
- расхождение между исходными ответами моделей;
- N/A, если включён review_na;
- указанная моделью неоднозначность;
- низкая самооценка уверенности (только экспериментальная эвристика, не калиброванная вероятность).

Один и тот же объединённый маршрут идёт всем моделям — сравнение остаётся парным. Отдельно измерить вклад каждого триггера отключением его в новой конфигурации. Неудачный JSON направляет на проверку все отсутствующие критерии.

Строгая проверка дополнительно к ядру: только точные допустимые значения шкал без округления; цитата — дословная непустая подстрока реально существующей реплики; обязательны объяснение и доказательство даже для N/A; для «Нет»/сниженной ступени нужен существующий упорядоченный checked_range. Дубли и лишние критерии — ошибки. Смысловую релевантность цитаты алгоритм не доказывает. При неполных ответах итог null, а не нормализованный балл по оставшимся критериям.

Правила надёжнее модели в арифметике, существовании idx, точности цитат, количестве/порядке реплик и вычислении временных интервалов. Они не надёжнее в оценке эмпатии, достаточности консультации, защищённости действия или возможности попрощаться. Regex совпадения приветствий, ожидания и концовок — только подсказки: отсутствие совпадения не доказывает нарушение. Текущие словари намеренно просты и неполны, особенно KZ; их покрытие нужно проверять на человеческих примерах. Порог 30 секунд — диагностический параметр, не правило организаторов.

Режим «правила вместо модели» сознательно не активирован: нет проверенной достаточности правил для полного критерия. Перспективный эксперимент — замена только формально доказуемых подпроверок, с воздержанием во всех остальных случаях. Это предложение следующей итерации, не реализованная функция.

## Токены и стоимость

Измерение сгенерированных входов на 8 одинаковых диалогах, на одну модель; эвристика `chars-per-script`, а не точный расход провайдера:

| Вариант | Исходных вызовов | Входных токенов | × к V1 |
|---|---:|---:|---:|
| V1 / первая стадия review | 8 | 30 413 | 1,00 |
| sections | 32 | 99 220 | 3,26 |
| hints | 8 | 31 123 | 1,023 |

Для трёх моделей: 24 / 96 / 24 исходных ручных вызовов соответственно; входные токены умножаются на 3. После route реальный размер повторных запросов записан в routing.json. Грубая плановая оценка V5 при r=25%: 10 вызовов и ~38 016 входных токенов на модель; при r=50%: 12 и ~45 620. Это предположение о размере дополнительного запроса, не измерение и не гарантия экономии.

Выход заранее неизвестен: в конфиге плановый бюджет 650 токенов на критерий, то есть 41 600 на модель для 8×8 критериев до перепроверки. V2 повторяет метаданные/схему на каждую секцию: эта простая оценка выхода может занижать накладные расходы. У review дополнительный выход также измеряется после ответов, не включён в исходный бюджет. Формула стоимости: `(input_tokens × input_per_mtok + output_tokens × output_per_mtok) / 1e6`. При одинаковой цене входа/выхода исходная плановая полная стоимость V2 ~1,96× V1, hints ~1,01×; при других ценах соотношение меняется. Денежные цены оставлены null: конкретные версии моделей и тарифы пока не выбраны; никаких выдуманных актуальных цен.

Фактический сохранённый ответ считается через общий tokens-модуль. Точные счётчики можно положить в `responses/<имя>.usage.json`: `input_tokens`, `output_tokens`, `model`. Без них используются оценки. report.json содержит измеренные расходы отдельно от projection; jury-proposals.json — согласие. Согласие не является точностью или вероятностью правильности.

## Проверяемые тезисы и протокол

| Тезис | Эксперимент | Признак пользы |
|---|---|---|
| V5 приближает качество к дорогой декомпозиции | одинаковые диалоги/модели, V1 против V5 и V2 | меньше ошибок при меньших токенах, чем V2 |
| Подсказки дают пользу почти бесплатно | V1 против hints с тем же шаблоном | изменение точности, валидности доказательств; стоимость +2,3% входа в пилоте |
| Проверка ловит формальные ошибки | сохранить исходный ответ, считать отклонения до исправления | доля ошибочных цитат, шкал, пропусков; точность после ответа отдельно |
| Согласие выявляет риск ошибки | разметить также случайные согласованные случаи | ошибка в согласованных против спорных, coverage/risk |
| Независимая проверка снижает якорение | blind review против review с показанным исходным ответом | доля исправлений и доля внесённых ошибок |

До сравнения точности: человек размечает ответы и доказательства; обсуждает неоднозначности; фиксирует отложенную часть, недоступную настройке. Для каждого варианта одинаковый набор, модель/версия и условия; повторные независимые прогоны на части выборки. Считать точность по критериям/макро, путаницу no/na, MAE итогов, precision/recall флагов, валидность цитат и совпадение idx с эталоном, токены/вызовы на диалог. Для V5 дополнительно долю направленных на проверку, исправления и новые ошибки, долю ошибок вне маршрута. Парный bootstrap выполнять по диалогам, а не считать 64 критерия независимыми наблюдениями. На 8 намеренно отобранных диалогах нельзя заявлять общий выигрыш или статистическую значимость. Метрики качества пока описаны как протокол, вычислителя эталонных метрик здесь нет.

Калибровка уверенности: пока только наблюдаемая доля согласия с n, `calibrated_probability: null`. После появления решений людей — обучить калибратор на отдельной части (согласие, длина, язык, канал), проверить Brier/ECE и coverage/risk на hold-out. Не обучать и не проверять на тех же апелляциях; нужны случайные аудиты. Обучаемый калибратор в этой версии не реализован.

## Версии и изменение чек-листа

prepare фиксирует полный снимок чек-листа, конфигурацию, нормализованные диалоги, хеш шаблона и исходников зависимостей. Добавление/отключение/удаление/смена типа критерия подхватываются новым prepare. Группы sections выводятся из активного чек-листа; review тоже использует текущие активные критерии. Никаких таблиц специальных id. Предыдущий прогон закреплён за снимком, не за latest. Если код изменился после prepare, ingest/route останавливаются: нужно сохранить старую версию кода или подготовить новый прогон. Если изменён шаблон, route также останавливается. Тесты проверяют произвольный новый id и полный файловый цикл.

В variants/codex/runs/<run>/validated/<agent>/<id>.json — формат базы (answers, criteria, issues, usage, score, checklist, agent, conversation_id) с дополнительными полями variant/pending/review_proposal. Сырые ответы не переписываются кодом. Каждая производная оценка сохраняется также в snapshots/<hash>/…, действия — в локальный append-only events.jsonl. validated — обновляемое представление последнего ingest, не архив. Отчёт тоже пересобираемое представление. Общий history/events.jsonl не затрагивается.

## Риски и предложения другим

- Повтор той же модели может повторять ошибку; большинство коррелированных моделей тоже ошибается. Проверять на людях и сохранять исходные ответы.
- Самоуверенные ошибки и ошибки без формальных нарушений не попадут в маршрут: нужен случайный аудит вне маршрута.
- В V2 исходный шаблон содержит пример c01 даже для других секций. scope и список ids имеют приоритет; в общей зоне стоит сделать пример схемы динамическим.
- Общему ядру: не округлять невалидную ступень автоматически, проверять checked_range, явно различать partial и полноценный итог. Здесь это реализовано изолированно.
- Владельцу платформы: подключить review_proposal к явному действию человека и сохранить ссылку на выбранный источник доказательств; не заменять человеческие решения голосованием.
- Antigravity: использовать те же 8 ID для пилота, общую формулу и одинаковую процедуру ручного запуска; сравнить затраты на повтор полного диалога при замене одного критерия.
- Идея следующего эксперимента: выбирать спорные критерии по измеренному ожидаемому снижению ошибки на дополнительный токен; флагам с нулевым весом сохранять отдельный приоритет, иначе денежная оптимизация их скроет. Пороги утверждает человек.

Проверено: 5 собственных тестов (строгая шкала/цитаты, новый id, расхождение, двухэтапный ручной цикл без замены исходного результата, V2/ошибочный JSON) и 12 существующих тестов ядра. Все прошли. Ответы в тестах — искусственные однообразные fixtures, не оценки DEV.
