## Обсуждение 0. Предыстория: разбор задачи до фазы 1

> Сжатая запись первых обсуждений (до того, как начали вести журнал дословно). Подробности — в [plan.md](plan.md).

### 0.1. Первичный разбор материалов

- Изучены все документы в `docs/`: задание ([task.md](../organizers/task.md)), чек-лист ([checklist.md](../organizers/checklist.md)), критерии отбора ([criteria.md](../organizers/criteria.md)). Третий PDF — презентация компании ([company.md](../organizers/company.md)), к задаче не относится.
- Скачан DEV-набор: 65 диалогов — 60 синтетических чатов (30 RU, 15 KZ, 15 EN) и 5 реальных звонков (RU). В гайде «35 RU» = чаты + звонки.
- Наблюдения по данным:
  - структура чата всегда одна: вопрос клиента → бот AIM → эскалация → оператор → иногда системное событие о завершении;
  - оцениваем только оператора, бот и system — контекст;
  - концовки чатов разные («Оператор закрыл чат», «Соединение прервано», «Клиент покинул чат») — влияет на критерий 07;
  - синтетические чаты, похоже, проверяют каждый свою «ловушку»;
  - звонки — шумный ASR, маски `[Имя скрыто]`, ISO-время;
  - `audio_url` ведёт на HTML-плеер с mp3, подписанным примерно на час;
  - эталона (Ground Truth) в DEV нет.
- Первые рекомендации: LLM определяет ответы, код считает баллы; промпт строится из чек-листа; своя ручная разметка 15–20 DEV-диалогов и скрипт оценки точности; голосование нескольких прогонов; стек FastAPI + SQLite + чистый JS.

### 0.2. Спорные места и развилки

- **Спорные трактовки критериев** (где легче всего разойтись с эталоном):
  - 01 — язык клиента в KZ-чате, если клиент пишет по-русски; «Hi, I'm Leo» = приветствие + представление;
  - 02 — граница «Да» / N/A, если данных хватало сразу (`p1-ru-001`);
  - 03 — что считать защищённым действием;
  - 04 — повтор ответа бота как косвенный ответ (`p1-ru-012`) — 20 или 15;
  - 06 — какая пауза считается «явным ожиданием» (порог первой реакции 3 мин исключён);
  - 07 — клиент ушёл / связь прервалась без прощания — «Нет» или N/A (`p1-ru-012`);
  - 08 — флаг за само предложение, без согласия клиента.
- **Звонки:** тот же чек-лист + отдельная инструкция (шумный ASR, грамотность по тексту не оцениваем, звук не анализируем).
- **Метрика точности организаторов неизвестна** (по критериям / по итогу / по флагу) — стоит спросить; по умолчанию оптимизируем совпадение по критериям.
- **Развилки:** один вызов на весь чек-лист или по критерию; своя разметка обязательна; голосование прогонов — да.

### 0.3. Суть, цель, критерии отбора, инициализация

- **Суть:** автоматизация отдела контроля качества (QA) контакт-центра брокера. Четыре свойства: объяснимость, настраиваемость, человек в контуре, встраиваемость в Dynamics 365. LLM — быстрый «первый проверяющий», а не судья.
- **Цель в две ступени:** (1) топ-50 — решает точность на 10 скрытых транскриптах; (2) защита за 5 минут — решает отполированный сценарий.
- **Критерии отбора и выводы:**
  - точность — главный, нужна стабильность и буквальное следование чек-листу;
  - функциональность — сначала обязательное, потом 1–2 «фишки»;
  - удобство — всё из демо в 1–2 клика;
  - корректность процесса — ни одного критерия в коде, видимый процесс;
  - разнообразие — шанс выделиться гибридом облако + локальная модель;
  - план презентации — фактически приёмочный тест.
- **Инициализация:** чек-лист из PDF — версия v1 по умолчанию; DEV загружается через API, `group_id` задаётся в интерфейсе. Предложена схема чек-листа (секции, типы `binary` / `scale` / `flag`, условия N/A, `global_rules`, правила расчёта) — реализована в [../data/checklists/default/v1.json](../../data/checklists/default/v1.json).

- Чек-лист — в JSON; DEV-набор разложен по файлам: `raw.json`, `conversations/*.json` (с номером реплики `idx`), `transcripts/*.md`, `index.md` / `index.csv`.
- Скрипт [../scripts/fetch_dataset.py](../../scripts/fetch_dataset.py) скачивает любой `group_id`; ссылка на API — в `.env`.

### 0.5. Фаза 1: что должно быть готово и черновики контрактов

- **Смысл фазы 1 (0–2 ч):** после неё никто ни на кого не ждёт — фронтенд, бэкенд и промпты работают параллельно по общим контрактам и мокам.
- **Критерий завершения:** выбраны модель, стек, роли; зафиксированы контракты; каркас отдаёт мок-оценку, фронтенд её показывает; договорились о процессе разметки.
- **Черновик ответа LLM** (без баллов): `criterion_id`, `answer` (yes / no / na / число), `evidence[{idx, quote}]` (цитата проверяется кодом против галлюцинаций), `checked_range` (для пропущенного действия), `explanation` (всегда на русском). Предложено брать уверенность из согласия прогонов, а не из самооценки модели.
- **Черновик результата оценки:** ссылка на версию чек-листа, модель, число прогонов; по критериям — ответ, баллы, вес, `effective_weight` (после перераспределения N/A), доказательства, согласие, поле `final` для решения по апелляции; секции, итог (`null`, если нечего считать), флаг грубой ошибки, статус. Исходная оценка не меняется.
- **Черновик REST API:** загрузка набора, список и карточка диалога, CRUD чек-листов (PUT = новая версия), запуск оценки (батч), апелляции и решения, свежая ссылка на аудио. Предложено запускать оценку в фоне с прогрессом.
- **Процесс разметки:** 15 диалогов (6 RU, 4 KZ, 3 EN, 2 звонка, разные концовки), два независимых разметчика, расхождения = спорные трактовки → `global_rules`; формат `eval/ground_truth.json`.

### 0.6. Решение: облачные агенты вместо LLM API на время разработки

- **Решено:** пока не подключаем API и локальные модели. Облачные агенты (Claude Code, Codex, Antigravity) работают как замена LLM API: получают тот же сгенерированный системой промпт и отвечают в том же формате. Агенты — не оценщики продукта, а временный «провайдер».
- **Учтённые отличия агента от API:** агент видит репозиторий (изоляция контекста), рассуждает многошагово (точность может быть завышена), не должен получать несколько диалогов в одной сессии, может быть другой моделью, чем финальная; нет контроля температуры.
- **Архитектура:** подключаемый провайдер LLM; первый — файловый адаптер (`runs/<run_id>/prompts/*.md` → ответы агентов → импорт); ближе к API — неинтерактивный режим `claude -p` / `codex exec` / `gemini -p` по скрипту.
- **Граница:** файловый режим — только для разработки. Переход на API или локальную модель — к ~16–18 ч, чтобы на контроле и защите система оценивала сама.
- **Три агента как три разметчика:** их расхождения автоматически показывают спорные трактовки; эталон — решение людей по расхождениям, а не голый вывод агента.

### 0.7. Объяснение задачи с нуля

Записано для команды: заказчик (Freedom Broker, чаты поддержки), проблема (ручной контроль качества покрывает малую часть диалогов), что строим («робот-контролёр», которому можно доверять: объясняет, можно оспорить, правила меняются через интерфейс), как нас оценят (точность на 10 скрытых диалогах + 5-минутная защита), как достигнем (модель думает — программа считает; агенты на разработке, настоящая модель к концу).

## Обсуждение 1. Декомпозиция пайплайна на сабтаски и эксперименты

**Статус:** открыто — ждёт решений по вопросам в конце.

### Предложение (Алтай)

> Так, начинаем тогда фазу 1. Для первой итерации нужно обсудить план. По разделению самого пайплайна на максимальное количество, точнее, на оптимальное количество сабтасков, где на каждом сабтаске у нас будет возможность вручную менять, манипулировать данными, промптом, чек-листом, критериями и другими параметрами. Чтобы наш пайплайн полностью был открытым, без, получается, блэкбоксов. И нужно посмотреть, точнее, я считаю, что нужно провести эксперименты и тесты по разделению на разное количество сабтасков, где в каждом сабтаске у себя будет, например, какой-то агент или какой-то алгоритм или классический ML-алгоритм, который будет считать те или иные метрики.
>
> Например, мы можем дать одному агенту оркестрацию полностью пайплайна, то есть через этого агента, например, будет проходить edit промпта, чек-листов, критерии. Потом для каждого критерия, например, можно будет вызывать отдельно модель, которая будет, получается, выдавать ответ с какими-то цитатами, точнее, с reasoning. И в конце будет, например, классический ML-алгоритм, который будет считать по вот этой таблице балл оператору. И в конце это все будет выводиться в, например, какой-то output, какую-то таблицу. Это тоже будет, например, заниматься этим какой-то алгоритм простой.
>
> И этот output, получается, будет идти к начальному главному оркестратору агенту, который, опять-таки, будет менять свои суждения. Например, если мы хотим добавить новый чек-лист, новые критерии, или убрать критерии, то мы вписываем это на сайте, на платформе, и вот этот главный агент, он, получается, подправляет чек-лист, создает новую, например, итерацию, дает новый промпт, и потом уже эти промпты прогоняются по разным субагентам, или, может быть, по одному агенту. Потом он вводит, например, еще одну таблицу, и по этой таблице прогоняется уже ML-алгоритм.
>
> Получается, это closed-loop система, и я считаю, что чтобы наша идея была продаваемая и чтобы мы могли доказать тезис того, что наша система оптимальная, нам нужно просто протестировать пару вариантов, сравнить метрики, и показать, почему эта система выигрывает и какое оптимальное количество, например, сабтасков нужно в системе.

### Ответ (Claude)

Идея сильная, особенно с точки зрения продажи решения: «у нас нет чёрных ящиков, и мы доказали цифрами, почему архитектура именно такая». Её стоит взять в основу. Но сначала нужно развести два разных понятия, которые в описании смешались. Потом — по компонентам: где согласен, а где предлагаю иначе.

#### Две разные оси «сабтасков»

**Ось А — этапы пайплайна.** Что происходит с диалогом от загрузки до итоговой таблицы. Этапов фиксированно около десяти, большинство из них — обычные алгоритмы. Тут экспериментировать не с чем: это архитектура, и требование одно — каждый этап открыт и редактируем.

**Ось Б — декомпозиция суждения LLM.** Сколько вызовов модели делать на один диалог: один на все критерии, по секциям, по одному на критерий, с проверяющим или без. **Именно здесь вопрос «какое количество сабтасков оптимально» и решается экспериментом.**

Если их не разделить, эксперимент превратится в «сравниваем всё со всем», и выводов не будет.

#### Ось А: пайплайн без чёрных ящиков

Каждый этап получает на вход файл и отдаёт файл. Любой из них можно открыть, поправить руками и перезапустить пайплайн с этого места.

| # | Этап | Кто выполняет | Артефакт (что можно править) |
|---|---|---|---|
| S0 | **Конфигурация** | человек / оркестратор | `checklist.json`, `global_rules`, шаблоны промптов — всё с версиями |
| S1 | **Нормализация** диалога | алгоритм | `conversation.json`: номера реплик, нормализованное время |
| S2 | **Извлечение признаков** | алгоритм | `features.json` (детали ниже) |
| S3 | **Сборка промптов** | алгоритм | `prompts/*.md` — ровно то, что увидит модель |
| S4 | **Суждение** | LLM / агент | `raw/*.json`: ответ, рассуждение (reasoning), цитаты, номера реплик |
| S5 | **Валидация** | алгоритм | `validated.json` + `errors.json`: формат, допустимость N/A, совпадение цитаты с репликой |
| S6 | **Агрегация** прогонов и агентов | алгоритм | `aggregated.json`: итоговый ответ + согласие (3/3, 2/3) |
| S7 | **Расчёт баллов** | формула | `score.json`: баллы, веса после N/A, секции, итог, флаг грубой ошибки |
| S8 | **Вывод** | алгоритм | таблица / CSV / карточка в интерфейсе |
| S9 | **Сравнение с эталоном** (только при разработке) | алгоритм | `metrics.json`: точность по критериям, ошибки |
| S10 | **Обратная связь** | оркестратор + человек | предложение правок к S0 → новая версия |

В S2 алгоритмы детерминированно, без LLM, извлекают:
- первую реплику оператора;
- язык клиента;
- паузы между репликами;
- кто завершил чат;
- момент эскалации;
- маски персональных данных.

Это «бесплатные» факты, которые модель часто путает. Мы их подсказываем.

Каждый прогон складывается в `runs/<run_id>/s01…s09/`. Тогда в интерфейсе можно показать «как система пришла к этому баллу» по шагам. Это сильная фича для демо и прямой ответ на критерий «корректность процесса».

#### Ось Б: что сравниваем в эксперименте

| Вариант | Вызовов LLM на диалог | Гипотеза |
|---|---|---|
| **V1 Монолит** — все критерии одним вызовом | 1 | Дёшево, модель видит картину целиком, но может «смазать» тонкие критерии |
| **V2 По секциям** | 4 | Компромисс: связанные критерии вместе (например, консультация и ведение диалога) |
| **V3 По критерию** — каждому свой фокусный промпт | 8 | Лучше на тонких критериях (07, 08, N/A), но теряется общий контекст и в 8 раз дороже |
| **V4 Сначала факты** — 1 вызов извлекает факты (суть запроса, защищённые действия, концовка), потом суждения по фактам | 1 + 1…8 | Меньше галлюцинаций, рассуждение прозрачнее |
| **V5 V1 + проверяющий** — повторная проверка только спорных критериев (несогласие прогонов или «трудные» 02/07/08) | 1 + k | Ставка на оптимум: цена монолита, точность ближе к V3 |

Дополнительные «рычаги», которые можно включать в любом варианте:
- признаки из S2 (вкл / выкл);
- число прогонов (1 / 3);
- агент (Claude / Codex / Gemini).

**Метрики**

| Метрика | Зачем |
|---|---|
| **Точность по каждому критерию** | Главная, ровно так нас и будут мерить |
| Ошибка итогового балла (MAE) | Насколько близок итог |
| Путаница «Нет» ↔ «N/A» | Главная ловушка чек-листа, отдельно |
| Полнота (recall) по грубым ошибкам | Пропустить нарушение хуже, чем перестраховаться |
| Валидность доказательств | Существует ли реплика, совпадает ли цитата |
| Стабильность | Согласие между повторными прогонами |
| Стоимость и время | Токены и вызовы на диалог — FAQ прямо требует цену оценки |

Итог эксперимента — **таблица вариантов и график «точность против стоимости»**. Слайд «почему наша архитектура» готов.

#### Где предлагаю иначе

**1. ML для подсчёта балла — не нужен и даже вреден.** Балл по таблице — это формула, заданная чек-листом: веса, перераспределение N/A, округление. Задание прямо говорит применять правила из чек-листа. Обученная модель может только ошибиться там, где формула точна. К тому же у нас будет ~20 размеченных диалогов: на таком объёме ML переобучится.

Где классический ML действительно уместен:
- **в S2** — признаки: определение языка, паузы, статистика реплик;
- **в S6** — калибровка уверенности: простая логистическая регрессия по признакам «согласие прогонов + критерий + длина диалога» предсказывает, где модель скорее ошибается, и отправляет такие случаи на ручную проверку. Это честно, полезно и красиво звучит.

**2. Оркестратор не должен менять суждения сам по своему же выводу.** Если агент смотрит на результат и правит промпт без внешнего сигнала, замкнутый цикл подгоняет систему сама под себя, и точность не растёт. Цикл работает, только если обратная связь **внешняя**:
- **при разработке** — наш эталон (S9 → метрики → ошибки);
- **в продукте** — **решения проверяющих по апелляциям**. Проверяющий изменил оценку → это сигнал.

Тогда цикл выглядит так:

```
ошибки / апелляции → оркестратор анализирует → предлагает правку правил/промпта (diff)
→ человек подтверждает → новая версия чек-листа → прогон на эталоне
→ принимаем, только если метрика не упала
```

Это и продаётся лучше: **«система учится на апелляциях, человек контролирует каждое изменение»**.

**3. Оркестратор — не в каждой оценке, а в двух ролях:**
- **редактор чек-листа:** пишете по-человечески «добавь критерий: оператор предложил оценить обслуживание», агент превращает это в структурированный JSON, показывает diff, вы подтверждаете;
- **аналитик ошибок** в цикле выше.

Оценка самих диалогов (S1–S8) идёт без него. Так быстрее, дешевле и воспроизводимо.

#### Честные ограничения эксперимента

- **Статистика.** 20 диалогов × 7 критериев = 140 решений. Разница в 3–5% — это 4–7 решений, то есть на грани шума. Подавать результаты как «направление» и смотреть разбивку по критериям, а не одну цифру.
- **Объём на агентах.** V3 — 8 вызовов × 20 диалогов × 3 прогона = 480 вызовов только на один вариант. С `claude -p` по скрипту это реально, но упрёмся в лимиты подписок. Предлагаю сначала 1 прогон на всех вариантах, а 3 прогона — только для двух лучших.
- **Время.** Эксперименты ограничиваем жёстко, условно 6–14 час. Продукт (интерфейс, апелляции) от них не зависит и идёт параллельно на варианте V1.

### Ответ на комментарий 1 (Claude)

Согласен с главным: **решение проверяющего — это ground truth, а апелляции — топливо для обучения системы.** Это превращает второй контур из «формальности по ТЗ» в ядро продукта, и это сильнее, чем у большинства команд. Ниже — как это сделать так, чтобы цикл действительно улучшал систему, а не раскачивал её.

#### Что уточнить

**1. Учимся на закономерностях, а не на единичных случаях.** Проверяющий всегда прав в конкретном случае, но одно решение может быть исключением, а разные проверяющие могут решать похожие случаи по-разному. Если переписывать промпт после каждой апелляции, система будет метаться. Поэтому:
- каждое решение сразу сохраняется как **прецедент** (работает немедленно, см. механизм А ниже);
- правило в промпте меняется, когда накопилось несколько однотипных прецедентов (механизм Б).

**2. Оркестратор не оспаривает проверяющего, но подсвечивает противоречия.** Если новое решение противоречит действующему правилу или прошлому решению другого проверяющего, оркестратор не перезаписывает молча, а показывает конфликт: «это решение расходится с правилом X и прецедентом #12 — уточнить правило?». Это не спор с проверяющим, а защита от того, чтобы правила разъехались.

**3. Веса критериев оркестратор менять не должен.** Это главное возражение.
- Апелляция говорит «модель неправильно ответила по критерию 07», а не «критерий 07 менее важен». Вес — это **бизнес-политика** (что компания считает важным), а не параметр точности.
- Снизить вес спорного критерия — значит спрятать ошибку: апелляций станет меньше, потому что ошибка меньше влияет на балл, но сама ошибка останется. Это подгонка метрики.
- Эталон организаторов посчитан с весами из чек-листа. Если система сама сдвинет веса, мы гарантированно разойдёмся с эталоном.

Что можно: оркестратор **показывает аналитику** («критерий 07 даёт 40% апелляций, формулировка неоднозначна, вот примеры») и **предлагает** администратору чек-листа изменить формулировку или вес. Решает человек.

**4. Метрика «меньше апелляций» — недостаточная.** Апелляций может стать меньше и потому, что операторы перестали спорить. Честная метрика: **согласие модели с проверяющими** — на апелляциях и на случайной выборке, которую проверяющий смотрит без апелляции (аудит). Для хакатона: **кривая точности на нашем эталоне по версиям промпта** v1 → v2 → v3.

#### Что именно настраивает цикл (без дообучения модели)

| Механизм | Что происходит | Когда срабатывает | Риск |
|---|---|---|---|
| **А. Память прецедентов** | Решённая апелляция сохраняется: фрагмент диалога, ответ модели, решение проверяющего, причина. При оценке похожие прецеденты по тому же критерию подставляются в промпт как примеры | Сразу после решения | Низкий: это примеры, а не правила |
| **Б. Уточнение правил** | Оркестратор обобщает несколько прецедентов в правило для `global_rules` или в пояснение к критерию, показывает diff, человек подтверждает | Когда накопилось N однотипных случаев | Средний — защищает регрессионный прогон |
| **В. Маршрутизация** | Критерии с высокой долей апелляций автоматически получают проверяющий шаг (V5), 3 прогона или пометку «проверить вручную» | По статистике апелляций | Низкий: стоит дороже, но не ухудшает |
| **Г. Подсказки-признаки** | Если ошибка из-за факта, который можно посчитать алгоритмом (пауза, концовка чата), — добавить признак в S2 | По разбору ошибок | Низкий |
| **Д. Веса** | Только аналитика и предложение человеку | — | — |

#### Защита от регрессии — обязательный шаг цикла

Любое изменение (А–Г) — это новая версия конфигурации. Перед принятием она прогоняется на:
- нашем эталоне;
- **всех ранее решённых апелляциях** — они превращаются в растущий регрессионный набор тестов.

Принимаем, только если ничего не сломалось. Иначе исправление одного случая тихо ломает три других. Старую версию всегда можно вернуть.

#### Как выглядит цикл целиком

```
оценка → апелляция → решение проверяющего (+ причина)          [ground truth]
   → прецедент в памяти (сразу влияет на похожие случаи)        [механизм А]
   → оркестратор: сравнивает reasoning модели и причину проверяющего,
     классифицирует ошибку (не понял правило / не увидел факт / неоднозначный критерий)
   → предлагает: правило (Б) / маршрут (В) / признак (Г) / аналитику по весам (Д)
   → человек подтверждает → новая версия → регрессионный прогон
   → принимаем, только если метрика не упала → следующие оценки идут по новой версии
```

#### Как это показать на защите (≈1 минута, сильнейший момент)

1. Апелляция по критерию → проверяющий меняет оценку и пишет причину.
2. Оркестратор показывает: «модель ошиблась, потому что…; предлагаю уточнить правило: …».
3. Подтверждаем → новая версия → прогон: «точность на эталоне 82% → 86%, регрессий нет».
4. Похожий диалог теперь оценён верно.

Это и есть «система учится на своих ошибках под контролем человека».

### Ответ на комментарий 2 (Claude)

Здесь мы сошлись: **веса редактирует админ, оркестратор предлагает и обосновывает, сам ничего не меняет.** Ниже — как сделать адаптивность весов честной, и почему отделение алгоритма оценки от LLM даёт нам больше, чем кажется.

#### 1. Алгоритм оценки — отдельный модуль (S7)

Да. Это чистая функция: `ответы LLM + конфигурация чек-листа → баллы, секции, итог`. Она не знает про LLM и не вызывает её.

Про «регрессию»: формула оценки — это **линейная модель**, но её коэффициенты (веса) **задаёт политика компании**, а не подбирает обучение. Регрессия как метод *подбора* коэффициентов по данным нам пригодится в другом месте — в аналитике для предложений по весам (п. 3).

Главный бонус отделения: **изменение весов не требует повторного вызова LLM.** Ответы по критериям уже сохранены, пересчёт итогов по всем диалогам — мгновенный и бесплатный. Админ двигает ползунок веса и сразу видит, как меняются итоги. Это хорошая демонстрация на защите.

#### 2. Как отличить «модель ошиблась» от «критерий переоценён»

Тут важная тонкость. Обычная апелляция говорит «ответ модели неверный» — это сигнал о **точности**, а не о **важности** критерия. Если копить все апелляции в «предложения по весам», мы будем занижать вес критериев, на которых модель просто чаще ошибается.

Решение — **тип апелляции**, который выбирает проверяющий при решении:

| Тип | Пример причины | Куда идёт сигнал |
|---|---|---|
| **(а) Ошибка оценки** | «Оператор попрощался в реплике #14, модель не заметила» | Промпт / правила / прецеденты (механизмы А–Г) |
| **(б) Критерий неприменим или неоднозначен** | «Для такого типа запроса проверка личности не нужна» | Уточнение формулировки / условия N/A |
| **(в) Ответ верный, но несправедливо влияет на итог** | «Да, не попрощался, но чат оборвал клиент — 5 баллов штрафа несоразмерны» | **Предложение по весам** |

Только тип (в) копится в статистику для весов. Так мы честно отделяем «система ошибается» от «регламент неудачен».

#### 3. Как оркестратор предлагает веса

Источники сигнала:
- доля апелляций типа (в) по каждому критерию;
- влияние критерия на итог: как часто именно он решает, попадёт ли оператор в «плохие»;
- **«подразумеваемые веса»** — тут и пригодится ваша регрессия. Если проверяющие ставят ещё и общую оценку диалогу («в целом 7/10») или есть бизнес-метрика (CSAT клиента, повторное обращение, жалоба), то регрессия этой оценки по ответам на критерии показывает, **какой вклад каждый критерий фактически вносит** в восприятие качества. Если подразумеваемый вес критерия 07 — 1%, а по регламенту он 5%, это обоснованный повод для предложения.

Что получает админ:
1. **Предложение**: «Снизить вес 07 с 5 до 3, поднять 04 с 20 до 22».
2. **Обоснование**: статистика, примеры апелляций, подразумеваемые веса.
3. **Симуляцию «что если»**: пересчёт всех прошлых оценок с новыми весами, сколько операторов сменят категорию, как изменится согласие с итоговыми оценками проверяющих.
4. Кнопки «принять» / «изменить» / «отклонить». Принятие → новая версия чек-листа.

Честное ограничение: для подразумеваемых весов нужны данные, которых в хакатоне нет (общие оценки проверяющих, CSAT). Механизм показываем на прецедентах из демо, а регрессию — как заложенную возможность с понятным описанием.

#### 4. Для хакатона: эталон считается с весами из чек-листа

Контрольный эталон организаторов посчитан с весами из PDF. Поэтому **оценку для сдачи всегда делаем на версии чек-листа по умолчанию**, а адаптацию весов показываем как функцию продукта на отдельной версии («песочница»). Версионирование это и так даёт.

#### 5. «Никаких захардкоженных значений» — реестр параметров

Всё, что влияет на результат, живёт в конфигурации с версиями и редактируется в интерфейсе:

| Группа | Параметры |
|---|---|
| Чек-лист | критерии, формулировки, секции, тип ответа, ступени шкалы, условия N/A, **веса** |
| Расчёт | метод перераспределения N/A, округление, правило «итог не считается», отображение флага |
| Правила | `global_rules`, пояснения к критериям, прецеденты |
| Признаки (S2) | порог паузы для «явного ожидания», список концовок чата, словари защищённых действий |
| Суждение (S3–S4) | шаблоны промптов, вариант декомпозиции (V1–V5), модель/провайдер, температура, число прогонов |
| Агрегация (S6) | правило голосования, порог согласия для «проверить вручную» |
| Цикл обучения | сколько однотипных прецедентов нужно для правила, сколько прецедентов подставлять в промпт, пороги для предложений по весам |

#### Уточнение: что такое «тип апелляции» (по вопросу Алтая)

**Зачем.** Апелляция сама по себе говорит только «я не согласен». Но за несогласием стоят разные причины, и каждая должна менять **разную часть системы**. Если их не различать, цикл обучения будет крутить не те ручки: например, занижать вес критерия, на котором модель просто плохо видит факты.

**Кто и когда ставит тип.** Оператор подаёт апелляцию как обычно: критерий + комментарий. Тип определяет **проверяющий в момент решения** — один клик из четырёх вариантов плюс текстовая причина. Оркестратор может заранее предложить тип по тексту причины, проверяющий подтверждает или меняет.

**Как проверяющий выбирает тип — три вопроса по порядку:**

```
1. Ответ модели неверен по действующим правилам чек-листа?
   └─ да  → A. Ошибка оценки
   └─ нет / правила не дают однозначного ответа ↓
2. Правила покрывают эту ситуацию однозначно?
   └─ нет → B. Пробел в правилах
   └─ да ↓
3. Ответ верный, правило ясное — но последствие для итога соразмерно?
   └─ нет → C. Несоразмерный вес
   └─ да  → D. Апелляция необоснованна
```

**Четыре типа**

| Тип | Что значит | Решение по баллу | Куда идёт сигнал |
|---|---|---|---|
| **A. Ошибка оценки** | Модель ошиблась при ясных правилах: не увидела реплику, перепутала «Нет» и N/A, неверно поняла критерий, привела несуществующую цитату | **Меняется**, итог пересчитывается | Промпт, прецеденты, признаки S2 (механизмы А, В, Г) |
| **B. Пробел в правилах** | Правила не дают однозначного ответа для такой ситуации; проверяющий решает сам, как правильно | По решению проверяющего | Уточнение формулировки критерия, условия N/A или `global_rules` (механизм Б, с подтверждением админа) |
| **C. Несоразмерный вес** | Ответ верный, правило ясное, но штраф/вклад в итог несправедливо велик или мал | **Не меняется** — действует регламент | Статистика для предложений по весам или по типу критерия |
| **D. Необоснованна** | Модель права, правило ясное, последствие нормальное — оператор просто не согласен | Не меняется | Подтверждение точности модели (позитивный сигнал) |

**Примеры на наших данных**

- **A.** Модель поставила «01 Установление контакта — Нет: оператор не представился», а в реплике #10 написано «Меня зовут Алина». Модель пропустила факт → оценка меняется на «Да», случай становится прецедентом для критерия 01.
- **B.** `p1-ru-012`: клиент написал «Ок, это всё», через 18 секунд «Соединение с клиентом прервано». Модель: «07 Завершение — Нет». Оператор: «клиент ушёл, я не успел попрощаться». Чек-лист не говорит, сколько времени считается «возможностью завершить». Проверяющий решает «N/A» и отмечает пробел → оркестратор предлагает правило: «если клиент сам завершил разговор и связь прервалась в течение N секунд после его последней реплики — N/A».
- **C.** «05 Эмпатия — Нет»: клиент пожаловался на задержку вывода средств, оператор ответил корректно по сути, но не отреагировал на недовольство. По правилу ответ верный. Но бинарный критерий с весом 15 наказывает за одну сухую фразу так же, как за полное игнорирование жалобы. Балл остаётся, сигнал копится. Если таких случаев много, оркестратор предлагает админу снизить вес **или сменить тип критерия с «Да/Нет» на шкалу** — так тип C даёт предложения не только по весам, но и по устройству критерия.
- **D.** Оператор оспаривает «06 Ведение диалога — 7»: по его мнению, ответ был понятен. Но клиент переспросил из-за путаной формулировки. Проверяющий подтверждает оценку.

**Что это даёт системе и аналитике**

- **Точность модели на апелляциях** = доля B (где проверяющий подтвердил ответ модели) + C + D. Это честная метрика: отклонённая апелляция — доказательство, что модель была права.
- **Доля A по критериям** показывает, где в первую очередь чинить промпт.
- **Список B** — это готовый перечень пробелов в чек-листе для админа. Полезно компании даже без LLM.
- **Накопленные C** — обоснованные предложения по весам и типам критериев. Мы не путаем их с ошибками модели.
- **D** показывает, кто из операторов спорит чаще всего и по каким критериям — сигнал для обучения операторов.

### Ответ на комментарий 3 (Claude)

Полностью согласен — и это уже заложено в основу: промпт собирается из чек-листа, в коде нет критериев. Но «изменение сразу идёт в LLM» — это только верхушка. Чтобы изменение действительно распространялось **через все этапы**, нужно продумать четыре вещи: что считать критерием, как изменение проходит по этапам, что происходит со старыми данными и сколько стоит пересчёт.

#### 1. Критерий — самодостаточный «пакет»

Всё, что относится к критерию, хранится вместе с ним, а не размазано по коду:

| Часть пакета | Этап | Пример для 07 «Завершение» |
|---|---|---|
| Определение: название, «Да» / «Нет», условие N/A, тип, шкала, вес, секция | S0 | из чек-листа |
| Фрагмент промпта и подвопросы | S3 | «подвёл итог или предложил помощь?», «попрощался?» |
| Привязанные признаки | S2 | F.19 тип концовки, F.20, F.21 прощание |
| Правила валидации и зависимости | S5 | доказательство — последняя реплика оператора или системное событие |
| Примеры и прецеденты | S3, S10 | решённые апелляции по 07 |
| Статистика | S9, S10 | точность, доля апелляций по типам |

Добавили критерий — появился пакет. Удалили — пакет **архивируется**, а не стирается: его история, апелляции и прецеденты остаются доступны для старых оценок. Все этапы читают только активную версию чек-листа, поэтому сами «узнают» об изменении.

#### 2. Как каждое изменение проходит по этапам

| Изменение | S2 Признаки | S3 Промпт | S4 LLM | S5 Валидация | S6 Агрегация | S7 Баллы | S9 Эталон | S10 Цикл |
|---|---|---|---|---|---|---|---|---|
| **Добавить критерий** | привязать существующие / предложить новые | новый фрагмент | оценить новый критерий | новые правила | — | новый вес, перераспределение | ⚠️ нет разметки — разметить | новая статистика с нуля |
| **Удалить критерий** | отвязать | убрать фрагмент и упоминания в `global_rules` | ничего, если декомпозиция позволяет | убрать зависимости | — | пересчёт без него | исключить из метрик | открытые апелляции закрыть, прецеденты в архив |
| **Изменить формулировку** | проверить привязки | обновить фрагмент | переоценить этот критерий | проверить правила | — | пересчёт | ⚠️ разметка может устареть | прецеденты пометить «к старой формулировке» |
| **Изменить тип** (Да/Нет → шкала) | — | новый формат ответа | переоценить | новая схема | новое правило голосования | новая формула | переразметить | — |
| **Изменить условие N/A** | — | обновить | переоценить | — | — | пересчёт | проверить | — |
| **Изменить вес / секцию** | — | — | **ничего** | — | — | мгновенный пересчёт | — | — |

#### 3. Предпросмотр последствий перед сохранением

Удаление или изменение критерия — серьёзная операция, поэтому до сохранения система (оркестратор + алгоритм зависимостей) показывает, что затронется:

> «Удаление критерия 03 "Идентификация": 
> — правило №4 в `global_rules` упоминает идентификацию — удалить или переписать?
> — 2 открытые апелляции по 03 будут закрыты;
> — 7 прецедентов уйдут в архив;
> — признаки F.13, F.14 больше ни к чему не привязаны;
> — веса остальных критериев перераспределятся: 01 → 12.5, 02 → 18.75 …;
> — переоценка: 0 вызовов LLM (при декомпозиции по критериям) / 65 вызовов (при монолите).»

Человек подтверждает → новая версия чек-листа. Это же сильный момент для защиты, где жюри просит заменить критерий.

#### 4. Старые оценки и «изменение между итерациями»

- **Оценка привязана к версии.** Каждая оценка хранит версию чек-листа, по которой сделана. После изменения старые результаты не исчезают — можно сравнить «до / после».
- **Политика переоценки** (параметр): переоценить всё сразу / только выбранные диалоги / при открытии карточки.
- **Изменение посреди батча.** Батч закрепляется за версией, с которой стартовал, иначе итоги в одном наборе окажутся несравнимыми. Новая версия применяется к следующему запуску, либо текущий батч можно остановить и перезапустить.
- **Новый id для заменённого критерия.** Если критерий заменили по смыслу, он получает новый id, чтобы старые апелляции и прецеденты не начали ссылаться на другой критерий.

#### 5. Адаптивность — аргумент в эксперименте по декомпозиции

Ваше требование добавляет в эксперимент оси Б две важные метрики:

- **Стоимость изменения** — сколько вызовов LLM нужно после правки чек-листа. Монолит (V1): любое изменение текста критерия = переоценка всего диалога. По критерию (V3): добавили один критерий = один вызов на диалог; удалили = ноль вызовов.
- **Интерференция** — меняются ли ответы по *нетронутым* критериям, когда добавляешь или удаляешь соседний. В монолите это вполне вероятно: новый критерий в промпте сдвигает внимание модели. Если так, монолит менее предсказуем при изменениях.

Возможно, именно это склонит выбор к V3 или к гибриду, даже если монолит окажется чуть точнее. Это хороший, честный аргумент для защиты.

### Ответ на комментарий 4 (Claude)

Принцип принимаю целиком и предлагаю записать его как **главное правило системы**: *правда — только от человека; пайплайн, включая LLM, — инструмент, который готовит черновик, приводит доказательства и аргументы, но ничего не решает и ничего не меняет сам.* Ниже — как устроить историю, чтобы она одновременно была выходной таблицей, аудитом и источником обучения.

#### 1. История — журнал событий, в котором ничего не перезаписывается

Главное свойство: **записи только добавляются** (append-only). Исходная оценка модели никогда не затирается решением проверяющего — решение ложится поверх отдельной записью. Поэтому всегда видно, что предложила модель, что решил человек и почему.

Сущности и связи:

```
conversation ─┬─ evaluation (версия чек-листа, прогон, модель, итог)
              │     └─ criterion_result (ответ, баллы, объяснение, доказательства, согласие)
              │            └─ appeal (кто, комментарий, вложения)
              │                   └─ decision (подтвердить/изменить, новый ответ, причина, тип A–D)
              │
checklist_version ── (каждая evaluation ссылается на неё)
run (батч: версия чек-листа + хеш конфигурации + модель)
proposal (предложение оркестратора: diff, обоснование, ссылки на решения) ── approval (кто принял/отклонил)
change_log (кто, что, когда, почему изменил: чек-лист, веса, промпт, параметры)
```

- **Итоговая оценка — это вычисляемое представление**, а не отдельная запись: ответы модели + решения проверяющих поверх → пересчёт той же функцией S7. Исходная, решение и итоговая видны всегда, как требует задание.
- **Прецеденты — тоже представление** над решениями, а не отдельная «правда».
- **Вложения апелляций** (файлы, скриншоты, фрагменты записи) хранятся как файлы, в истории — ссылка и хеш.
- Хранение: SQLite (таблицы выше) + артефакты прогонов на диске по ссылкам. Экспорт в CSV / JSON.

#### 2. Таблица истории как выход системы

Для интерфейса все события сводятся в одну **ленту истории** с фильтрами:

| Время | Событие | Диалог | Критерий | Кто | Было → стало | Причина | Ссылки |
|---|---|---|---|---|---|---|---|
| 10:02 | Оценка | p1-ru-012 | 07 | LLM (прогон r5, чек-лист v1) | — → Нет | «оператор не попрощался» | артефакты r5 |
| 10:15 | Апелляция | p1-ru-012 | 07 | оператор | — | «клиент ушёл, я не успел» | вложение |
| 10:20 | Решение | p1-ru-012 | 07 | проверяющий | Нет → N/A, тип B | «связь прервалась через 18 с» | — |
| 11:00 | Предложение | — | 07 | оркестратор | правило 07 | «3 похожих решения типа B» | решения #4, #9, #12 |
| 11:05 | Изменение чек-листа | — | 07 | админ | v1 → v2 | принял предложение | proposal #3 |

Срезы: по диалогу (в карточке), по оператору, по критерию, по версии чек-листа, по типу события. Это же готовый аудит для комплаенса.

#### 3. Как история превращается в «обучение» (вместо backpropagation)

Уточнение термина: настоящего backpropagation — изменения весов нейросети — здесь нет и не нужно. Наш аналог — **обучение на уровне промпта и правил**, и оно разделено на открытые шаги (подэтапы S10):

| Шаг | Кто | Что делает | Артефакт |
|---|---|---|---|
| **S10.1 Журнал** | система | записывает все события | таблицы истории |
| **S10.2 Выжимка** | **алгоритм** (запросы, агрегаты) | собирает из истории: решения по критериям, ошибки модели по типам A–D, похожие случаи, статистику | `digest.json` — можно открыть и проверить, что именно увидит LLM |
| **S10.3 Прецеденты в промпт** | алгоритм | для каждого критерия подставляет в промпт k похожих решений проверяющих: «модель сказала X, проверяющий решил Y, потому что Z» | раздел промпта в S3 |
| **S10.4 Предложения** | оркестратор (LLM) | по выжимке предлагает правки правил / промпта / признаков, предложения по весам; каждое — со ссылками на решения | `proposals/*.json` (diff + обоснование) |
| **S10.5 Решение** | **человек** | принимает / меняет / отклоняет; может и сам править промпт, правила, чек-лист напрямую | запись в `change_log` |
| **S10.6 Проверка и активация** | алгоритм + человек | регрессионный прогон (эталон + все решения) → человек активирует новую версию | метрики до / после |

Так меняют систему **и человек, и LLM**, но по-разному: LLM только предлагает, применяет и активирует — только человек. Любое изменение из любого источника одинаково записывается в историю.

Тонкость по S10.3: прецедент — это само решение проверяющего, поэтому подстановка его в промпт — не самодеятельность LLM, а применение человеческой правды. Предлагаю, чтобы прецеденты включались автоматически, но проверяющий мог отметить решение «разовое исключение — не использовать как прецедент» (вопрос 11).

#### 4. «LLM может давать аргументы в противовес»

Это полезно: проверяющий тоже ошибается, например не заметил реплику #14. Но аргумент должен помогать, а не давить.

- При решении проверяющий всегда видит исходное рассуждение модели и доказательства со ссылками.
- По кнопке «аргументы модели» LLM может дать контраргумент к причине проверяющего: «в реплике #14 оператор написал "Всего доброго" — возможно, прощание было».
- Решение проверяющего — финальное в любом случае. В истории фиксируется, видел ли он контраргумент и что решил.
- Если два проверяющих решили похожие случаи по-разному, система показывает конфликт старшему или админу — LLM не выбирает, кто прав.

Отдельный риск — **автоматизационное смещение**: проверяющий начинает соглашаться с моделью по инерции. Защита — необязательный «слепой режим»: проверяющий сначала читает диалог и фрагмент, а ответ модели видит после (вопрос 13).

#### 5. Права: кто что может

| Действие | Оператор | Проверяющий | Админ | Пайплайн / LLM / оркестратор |
|---|---|---|---|---|
| Черновая оценка | — | — | — | ✅ |
| Подать апелляцию | ✅ | — | — | — |
| Решить апелляцию (ground truth) | — | ✅ | ✅ | ❌ |

Для хакатона авторизация не нужна: роли переключаются в интерфейсе, а подача апелляции и её решение показываются как отдельные действия (как и требует задание).

### Ответ на комментарий 5 (Claude)

Согласен, и это закрывает вопрос 10: **ничего не удаляется, всё уходит в архив, version control обязателен.** Предлагаю устроить версии по аналогии с git — это понятная всем модель.

#### 1. Версия чек-листа = неизменяемый снимок (как коммит)

| Поле | Зачем |
|---|---|
| `checklist_id` + `version` | Какой чек-лист и какая его версия |
| `created_at` | Таймстемп |
| `author` | Кто изменил (админ / принял предложение оркестратора) |
| `reason` | «Сообщение коммита»: почему изменили, ссылка на предложение или решения |
| `parent_version` | Из какой версии получена — цепочка истории |
| `snapshot` | Полный JSON чек-листа на этот момент: все критерии, веса, шкалы, правила |
| `content_hash` | Хеш содержимого — одинаковые версии распознаются, подмена видна |
| `status` | активная / архивная |

- **Удаление чек-листа или критерия** = статус «архив», запись остаётся навсегда.
- **Активная версия** — указатель (как `HEAD` в git), отдельный для каждого профиля (чат / звонок).
- **Diff между любыми двумя версиями** вычисляется на лету: какие критерии добавлены, удалены, какие поля изменились.

#### 2. Критерий тоже версионируется

У критерия **постоянный id** и **ревизия**: `c07@r1`, `c07@r2`. Снимок чек-листа хранит список ревизий. Так видно, что «Завершение» в версии 3 сформулировано иначе, чем в версии 1, и какие оценки и решения сделаны по какой формулировке. Заменённый по смыслу критерий получает новый id (решение из комментария 3).

#### 3. Версионируется вся конфигурация, а не только чек-лист

Суждение зависит не только от чек-листа. Каждая оценка ссылается на полный набор версий:

```
evaluation → checklist_version + ревизии критериев
           + prompt_version (шаблоны промптов)
           + features_version (словари, пороги S2)
           + params_hash (декомпозиция, прогоны, голосование…)
           + model (провайдер, модель, версия)
           + run_id
```

Это даёт **полную воспроизводимость**: по любой оценке можно восстановить, что именно видела модель, и повторить прогон.

#### 4. Решение проверяющего — по какой версии он судил

Важная тонкость. Оценка сделана по v1, а апелляцию решают, когда активна уже v2. По умолчанию проверяющий судит **по версии оценки** (v1) — иначе это не проверка, а переоценка по новым правилам. Решение хранит ссылку на версию, по которой вынесено, и в карточке показываются **тексты критериев именно этой версии**. Так можно «понять суждение» проверяющего, как вы и хотите.

#### 5. «Машина времени»

Запрос «как всё было на момент T»: какой чек-лист был активен, какие критерии и формулировки, какие оценки и решения существовали. В интерфейсе — выбор даты или версии в истории и просмотр карточки в том виде, в каком её видели тогда.

#### 6. Как хранить много данных, но оптимально

| Что | Как хранить | Почему |
|---|---|---|
| Снимки чек-листов и конфигураций | **полные снимки** в БД, не дельты | Маленькие (~10 КБ), полные снимки проще и надёжнее; diff считаем на лету |
| Одинаковое содержимое | дедупликация по хешу | Неизменённая ревизия критерия не дублируется |
| Промпты и сырые ответы LLM | файлы `runs/<run_id>/…`, сжатые (gzip), в БД — метаданные и хеш | Самое объёмное; БД остаётся лёгкой |
| Метаданные вызовов | БД: токены, время, модель, стоимость, статус | Для аналитики и стоимости оценки |
| События истории | БД, только добавление | Решение 8 |
| Экспорт | чек-листы ещё и как файлы `data/checklists/<id>/v<N>.json` в git | Второй, «человеческий» version control, удобно ревьюить |

Оценка объёма: 65 диалогов × 8 критериев × 3 прогона — единицы мегабайт сырых ответов на прогон. Для хакатона храним всё без ограничений; политику хранения (сколько держать сырые ответы) оставляем параметром.

Опционально — **цепочка хешей**: каждая версия включает хеш родителя, и любую подмену истории видно. Для финансовой компании это сильный аргумент про аудит и комплаенс.

#### 7. Какие данные ещё стоит собирать

- По прогонам: промпты, сырые ответы, токены, время, модель, конфигурация, ошибки валидации, повторы.
- По решениям: время на решение, какие доказательства проверяющий открывал, видел ли контраргумент, слепой режим или нет.
- По изменениям: что предложил оркестратор и что из этого приняли, отклонили или изменили — это метрика полезности самого оркестратора.

### Ответ на комментарий 6 (Claude)

Принято: **люди — полноценные сущности системы со своими id и статистикой; на этом этапе ничего не происходит автоматически — каждое действие запускается кнопкой, решает человек.**

#### 1. Откуда взять id операторов — честная проблема данных

В выданных данных **нет поля оператора**. В чатах оператор представляется в тексте («Меня зовут Алина», «Я Илья», «Hi, I'm Leo»), в звонках имя скрыто (`[Имя скрыто]`). Проверяющих в данных нет вообще. Поэтому:

- **Справочник людей** в системе: операторы, проверяющие, админы — с id, именем, ролью, командой, языками, датой начала работы.
- **Оператор диалога** назначается при импорте: из поля источника, если появится; иначе система **предлагает** оператора по имени из представления (признак F.3), а человек подтверждает кнопкой. Для звонков с маской — назначается вручную.
- **Проверяющий** выбирается в переключателе ролей при решении апелляции. Назначение апелляции проверяющему — тоже кнопкой.
- Для демо заводим небольшой справочник (условно 10–15 операторов по именам из DEV и 3 проверяющих) — чтобы статистика была не пустой. В README честно указываем, что это демонстрационные данные.

#### 2. Как хранить, чтобы связей было максимум — схема «звезда»

Чтобы любую связь между переменными можно было посмотреть одним запросом, данные раскладываются на **факты** и **измерения**:

```
              operator   reviewer   criterion@rev   checklist_version
                  \          |            |              /
  ФАКТЫ:   criterion_result ── appeal ── decision ── proposal
                  /          |            |              \
          conversation (язык, канал, длина, тип концовки)   model / run
```

- **Факты** — события с числами: ответ по критерию, баллы, апелляция, решение, время на решение.
- **Измерения** — «по чему резать»: оператор, проверяющий, критерий и его ревизия, версия чек-листа, язык, канал, длина диалога, тип концовки, модель, прогон, дата.
- Любая статистика ниже — это группировка фактов по одному или нескольким измерениям. Новую связь можно посмотреть без изменения схемы.

#### 3. Статистика по оператору

| Показатель | Что показывает |
|---|---|
| Число оценок, средний балл, тренд по времени | Общий уровень и динамика |
| Доля «Нет» / средний балл по каждому критерию | Слабые места — для обучения оператора |
| Грубые ошибки: число и подвиды | Риски |
| **Число апелляций и доля апелляций** (апелляции / оценки) | Насколько часто спорит |
| **Успешность апелляций** (доля изменённых оценок) | Спорит по делу или нет |
| Распределение апелляций по типам A–D | Много D — спорит без оснований; много A — модель часто ошибается именно на его диалогах (возможно, его стиль сбивает модель) |
| Апелляции по критериям | С какими критериями не согласен |
| Сравнение со средним по команде | Контекст |
| Разбивка по языку и каналу | Где хуже |

#### 4. Статистика по проверяющему

| Показатель | Что показывает |
|---|---|
| Число решений, среднее время на решение | Нагрузка, вдумчивость |
| **Доля подтверждений / изменений** | «В основном не меняет оценку» — ваш пример |
| Направление изменений (балл вверх / вниз) | **Мягкость / строгость** |
| Изменения по критериям | Где расходится с моделью |
| Распределение типов A–D | Как классифицирует причины |
| **Согласованность с другими проверяющими** на похожих случаях | Стабильность суждений |
| Согласие с моделью | Склонность доверять модели |
| Влияние контраргумента (менял ли решение после него) | Насколько поддаётся аргументам модели |
| Слепой режим vs обычный | Есть ли автоматизационное смещение |
| Конфликты с решениями других | Где правила понимаются по-разному |

#### 5. Связи «оператор × проверяющий» и прочие

- **Пара оператор × проверяющий:** сколько апелляций оператора X решал проверяющий Y и с какой долей изменений. Если в одной паре доля изменений сильно выше, чем у того же проверяющего с другими операторами, — повод посмотреть (возможная предвзятость в любую сторону).
- **Модель × оператор / язык / канал / критерий:** где модель чаще ошибается по решениям проверяющих.
- **Критерий × всё:** доля апелляций, изменений и типов по каждому критерию.
- **Экран «связи»:** выбираешь две переменные (например, «доля апелляций оператора» и «средний балл») → график и корреляция. Это даёт исследовать данные, не зная заранее, что искать.

#### 6. Осторожность со статистикой о людях

- **Показывать размер выборки.** «Проблемный оператор» по трём апелляциям — это шум. Рядом с каждым показателем — n и, где уместно, доверительный интервал.
- **Никаких автоматических ярлыков.** Система показывает цифры, выводы делает человек — это прямо следует из решения 7.
- Статистика — для обучения и разбора, а не для автоматических санкций.

| 10 | Удалённые критерии — архив | закрыт решением 9 |
| 11 | Прецеденты | **только по кнопке «Использовать как прецедент»** (решение 11) |
| 12 | Контраргумент LLM | **по кнопке** (решение 11) |
| 13 | Слепой режим для проверяющего | переключатель у проверяющего, по умолчанию выкл *(трактовка)* |

И темы фазы 1, которые мы ещё не обсуждали:
- контракты: формат ответа LLM, результата оценки, REST API;
- состав команды и роли;
- процесс разметки эталона агентами (инструкция, выборка, формат);
- финальная модель для рантайма (~16–18 ч) и её стоимость.

### Решения

1. **Алгоритм оценки (S7) — отдельный модуль**, независимый от LLM: чистая функция «ответы + чек-лист → баллы». Изменение весов пересчитывает итоги без повторного вызова LLM.
2. **Веса гибкие и открытые**: редактирует админ в интерфейсе (новая версия чек-листа). **Оркестратор сам веса не меняет** — только предлагает с обоснованием и симуляцией «что если».
3. **Никаких захардкоженных значений**: все параметры пайплайна — в версионируемой конфигурации (реестр в ответе на комментарий 2).
4. **Апелляции типизируются (A–D)**: тип выбирает проверяющий при решении, оркестратор может подсказать. На предложения по весам влияет только тип C.
5. **Стадия дизайна — собираем максимум параметров**, отсеиваем потом экспериментами. Полный каталог параметров, признаков, метрик и протоколов по всем этапам S0–S10 — в [design-space.md](design-space.md).
6. **Полный контроль над чек-листом**: критерии добавляются, удаляются и меняются через интерфейс; изменение сразу распространяется через все этапы S0–S10 (промпт, признаки, валидация, баллы, эталон, цикл). Критерий — самодостаточный пакет; оценки привязаны к версии чек-листа.
7. **Главное правило системы: правда — только от человека.** Решение проверяющего — абсолютный ground truth. Пайплайн, включая LLM и оркестратор, — инструмент: готовит черновую оценку, приводит доказательства и контраргументы, предлагает изменения. Он не может менять решения проверяющих, параметры, веса, чек-лист или промпт, не может активировать версии — это делает только человек.
8. **История — журнал событий без перезаписи** (оценки, апелляции, решения, предложения, изменения конфигурации). Итоговая оценка и прецеденты вычисляются из журнала. Таблица истории — один из выходов системы и источник данных для обучения (S10.1–S10.6).
9. **Обязательный version control, ничего не удаляется.** Удалённые чек-листы и критерии уходят в архив. Версия чек-листа — неизменяемый снимок с id, номером, таймстемпом, автором, причиной, родителем и хешем; критерии имеют ревизии. Каждая оценка и каждое решение ссылаются на полный набор версий (чек-лист, промпты, признаки, параметры, модель) — по любой оценке можно восстановить, по каким правилам она сделана.
10. **Люди — сущности системы.** У каждого оператора, проверяющего и админа свой id. Хранятся все взаимодействия (апелляции, решения, назначения), статистика по оператору, проверяющему и паре «оператор × проверяющий». Данные раскладываются по схеме «факты + измерения», чтобы любую связь между переменными можно было посмотреть одним запросом. Статистика о людях показывается с размером выборки и без автоматических ярлыков.
11. **На этом этапе ничего автоматического.** Каждое действие (оценка, переоценка, прецедент, анализ оркестратора, применение предложения, регрессионный прогон, активация версии, контраргумент) запускается кнопкой, решает человек. Автоматические режимы остаются в каталоге как опции со значением «выкл».
12. **Все варианты и альтернативы — в эксперименты.** Все варианты декомпозиции V1–V5 и альтернативы на каждом этапе. Для каждого этапа формулируем тезисы и способ их проверки. Результаты (оптимальное число LLM-вызовов и агентов, оптимальный пайплайн) — аргументация в презентации.
13. **Приоритет:** точность на контроле (первый отбор) и глубина цикла обучения и аналитики (решающий аргумент после) — сейчас в равном фокусе.
14. **Всё локально на этом устройстве.** Агенты: Antigravity, Codex, Claude Code; опционально бесплатные облачные open-source модели. API и локальных LLM пока нет.
15. **Стек пока не в фокусе.** Простые скрипты; главное — пайплайн, оркестрация, выбор моделей и сравнение их ответов.
16. **Расширенный ответ модели:** все учтённые факторы и полный reasoning, а не только ответ, номер реплики и цитата.
17. **Каждый диалог — через все модели «лоб в лоб»**, без деления между агентами. Токены считаем обязательно; ведём отчёт о затратах: по модели, по ансамблю моделей, по варианту декомпозиции (например, отдельный вызов на критерий).
18. **Итерация 1 — ручная.** Алтай вручную вставляет промпты в чаты агентов и переносит ответы; отправка и парсинг автоматизируются позже.
19. **Только выданный чек-лист.** Свои критерии — позже, по ходу прогонов.
20. **Id людей — простая нумерация:** `op-01…op-60` по именам операторов в чатах, `op-c1…op-c5` для звонков, проверяющие `r-01…`.
21. **Предполагаемая метрика организаторов** (не раскрыта): сравнение итогового балла и суждений — аргументов и цитат-доказательств. Объяснения пишем в стиле примера из чек-листа, цитаты — дословно.

Всё принято и записано в решения 12–21. Несколько практических замечаний к итерации 1.

**1. Объём ручной работы.** «Каждый диалог через все модели лоб в лоб» в ручном режиме — это много вставок:

| Вариант | Промптов на диалог | 65 диалогов × 3 агента |
|---|---|---|
| V1 монолит | 1 | 195 вставок |
| V2 по секциям | 4 | 780 |

Поэтому итерация 1 — **V1 на всех 65 диалогах × 3 агента**. V3 и остальные варианты — на подвыборке или после автоматизации. Способ сильно сократить ручную работу без API: открыть агента (Claude Code, Codex, Antigravity) в **изолированной папке**, где лежат только промпты, и попросить обработать файлы по одному и сохранить ответы файлами. Изоляция решает проблему «агент видит эталон», но остаётся риск влияния диалогов друг на друга в одной сессии — его фиксируем как фактор (L.10).

**2. Учёт токенов.** Чат-интерфейсы не всегда показывают расход. Поэтому: (а) входные токены каждого промпта считаем сами при генерации; (б) выходные — по сохранённому ответу; (в) если агент показывает расход (у Claude Code и Codex он виден), записываем его как точное значение. Стоимость = токены × цена модели (цены — параметр). Отчёт: по модели, по ансамблю моделей, по варианту декомпозиции.

**3. Расширенный ответ модели.** По каждому критерию модель возвращает не только ответ и цитату, но и все учтённые факторы: проверку применимости (N/A), ответы на подвопросы критерия, все рассмотренные реплики с интерпретацией (за и против), какое правило или ступень шкалы применена и почему не соседняя, неоднозначности в правилах, самооценку уверенности. Плюс факты уровня диалога (язык клиента, суть запроса, защищённое действие, тип концовки) и для проверки тезиса «LLM плохо считает» — собственный подсчёт итога моделью, который мы сравним с формулой.

**4. Предположение о метрике организаторов.** Сравнивают, вероятно, итоговый балл и суждения (аргументы, цитаты). Поэтому объяснение по каждому критерию пишем **в стиле примера из чек-листа**: «Завершение — Нет. … Основание — …», а цитаты — дословно из реплик.

**5. Id операторов.** В DEV у каждого из 60 чатов своё имя оператора (Алина, Тимур, Maya, Аружан…), в звонках имя скрыто. Рекомендация: `op-01…op-60` по именам из чатов, `op-c1…op-c5` для звонков, проверяющие `r-01…` — когда дойдём до апелляций. Попутно видно, что синтетические чаты содержат явные ловушки: предложение перевести деньги лично (`p1-ru-022`), оскорбление (`p1-ru-029`), ответы без приветствия или представления (`p1-ru-014`, `p1-en-015`, `p1-kz-008`).

| Контроль: набор выдают через 23 ч после старта, **1 час** на получение, оценку, проверку и push | Ручной режим: 10 чатов × 3 агента = 30 вставок для V1; для V3 — 240 | См. 2.3 |
| Контрольный набор — **только чаты** | DEV включает 5 звонков | Звонки важны для `results/dev` и демо, но на точность контроля не влияют |

Совпадения с уже принятыми решениями: S7 отдельно от LLM (решение 1), флаг отдельно, 1-based номера реплик, перераспределение N/A, статус ошибки вместо нуля. Переделывать ядро не нужно — нужен экспортёр и правка шаблона.

### 2.2. Факты: как будут отбирать и что спросят на защите

1. **Отбор без формулы.** Ориентиры: близость к GT на контроле, техническая проверка репозитория, функциональность и удобство, разнообразие подходов (баланс локальных LLM и облачных интеграций). Подгонять под неизвестную метрику не нужно.
2. **Точность — «в целом», не до балла.** Смотрят близость и адекватность оценки. Важно: разумная обработка N/A, грубых ошибок, неполных данных и спорных утверждений; **не придумывать факты при нехватке информации**; результаты **обоснованные и воспроизводимые**. По звонкам — учесть устную речь, идеального ASR не ждут.
3. **Защита = живое демо**, слайдов минимум. Примеры вопросов:
   - все диалоги с грубыми ошибками и объяснения, почему они так классифицированы;
   - как **оператор** отправляет оценку на апелляцию;
   - как изменить чек-лист: добавить критерий, изменить существующий, поменять вес;
   - результат оценки конкретного диалога с обоснованием баллов.
4. **Жюри может само поработать** с запущенным решением (например, на нашем ноутбуке) несколько минут.
5. **Интерфейс — для крупной компании:** руководители, директора, специалисты контроля качества, сотрудники. Строгий корпоративный стиль, без игрового оформления; нестандартные решения приветствуются.

### 2.3. Что это меняет: разбор

**1. «Реально работающий продукт, который анализирует новые диалоги» противоречит ручному режиму на демо.** Решения 14 и 18 (только ручная вставка промптов) годятся для экспериментов, но на защите жюри даст новый диалог или попросит переоценить после смены чек-листа — и ждать, пока человек вставит промпт в чат, нельзя. Плюс жюри может работать с системой само. Вывод: к демо нужен **хотя бы один автоматический провайдер** (облачный API или локальная модель) за абстракцией провайдера, которую уже делает сессия реализации. Ручной режим остаётся для экспериментов и сравнения агентов. → Q18.

**2. Разнообразие подходов — это шанс, а не риск.** Организаторы хотят баланс локальных и облачных решений. Гибрид (локальная модель для части этапов + облачная для сложных критериев, или локальная как запасная) — честный `mode: "hybrid"` и сильный аргумент. Эксперименты V1–V5 можно дополнить осью «локальная vs облачная модель на этапе». → Q20.

**3. Час на контроль — жёсткое ограничение для выбора финального пайплайна.** В ручном режиме 30 вставок V1 (10 чатов × 3 агента) за час — на пределе, учитывая получение данных, проверку и push; V3 вручную невозможен. С автоматическим провайдером время перестаёт быть узким местом, но нужен **запасной путь** (если API упал — ручной режим по одному агенту). Перед контролем — **репетиция на 10 DEV-чатах с таймером**, по шагам: получение → оценка → экспорт → проверка → commit → push. Новый параметр эксперимента: время на 10 диалогов (M.16). → Q22.

**4. `results/dev` — тоже обязательная сдача.** Все 65 диалогов DEV должны быть оценены нашей системой и выгружены до стоп-кода. Значит `r001` (или финальный прогон) надо завершить заранее, а не в последний час.

**5. «Не придумывать факты» и «воспроизводимость» уже заложены, их надо показать.** Проверка цитат и номеров реплик (S5), N/A как отдельный ответ, ссылка каждой оценки на полный набор версий (решение 9), голосование нескольких моделей. Добавить явно:
   - правило в промпте «недостаточно данных → сказать об этом, а не додумывать» и поле с признаком нехватки данных;
   - такие случаи и низкое согласие моделей → в очередь проверяющему (по кнопке, решение 11);
   - воспроизводимость: повторный прогон с теми же версиями даёт то же самое или показывает расхождение (метрика стабильности из каталога).

**6. Четыре вопроса жюри — готовые приёмочные сценарии.** Платформа должна проходить каждый от начала до конца:

| Сценарий | Наши решения | Чего не хватает |
|---|---|---|
| Все диалоги с грубыми ошибками + почему | S7 флаг, `c08`, объяснения и доказательства | Фильтр «грубые ошибки» в списке, объяснение `c08` на видном месте |
| Оператор отправляет оценку на апелляцию | Контур апелляций A–D, люди с id (решения 4, 10) | Роль **оператора** как инициатора апелляции (не только проверяющего) |
| Изменить чек-лист: добавить / изменить / вес | Версии чек-листа, критерий — самодостаточный пакет (решения 6, 9) | Сквозная проверка: новый критерий → промпт → валидация → баллы → экспорт; пересчёт весов без LLM (решение 1) |
| Результат диалога с обоснованием | S8 вывод, объяснения, доказательства | Экран диалога: реплики, подсветка доказательств, баллы, `effective_weight` |

**7. Смена чек-листа против фиксированных кодов экспорта.** Формат сдачи требует ровно 8 кодов организаторов, а на защите чек-лист будут менять. Это не конфликт: `results/*.json` всегда выгружается по **чек-листу организаторов** (`default@v1` или его версии, где у всех 8 критериев есть код экспорта). Если у активной версии нет полного соответствия кодам — экспорт в формат организаторов отказывает с понятной ошибкой, а внутренний экспорт работает с любым чек-листом. → Q23.

**8. Интерфейс.** Фронтенд делает Алтай (решение 15 и его собственные идеи). Фиксируем как ограничение: корпоративная аудитория из четырёх ролей, строгий стиль, представления по ролям (руководитель — сводка и тренды; контроль качества — очередь, апелляции, чек-лист; оператор — свои оценки и апелляция). Совместимость с Dynamics 365 остаётся.

**9. Техническая проверка репозитория.** Неизвестные внутренние критерии, но очевидно: README с запуском в одну команду, тесты проходят, нет секретов (`.env` уже в `.gitignore`), нет захардкоженных результатов, понятная структура. Отдельный пункт чек-листа перед стоп-кодом.

## Обсуждение 4. Свой эталон и симуляция цикла

### Предложение (Алтай)

> Для начала самим отметить текущий датасет. Наши отметки не совпадут с отметками оценщиков, но приближённо, зная критерии, отметить можно — и заодно просимулировать сам пайплайн: полная симуляция пригодится для тестов, и посмотрим, как система работает с ground truth. Реальные ответы мы всё равно не получим — значит, суть задачи не угадать правильные ответы, а построить систему, которая умеет адаптироваться под правильные ответы. … Я вместе с новым чатом размечу все данные, и это будет считаться ground truth для начала.

### Ответ (Claude)

Согласен с обоими тезисами. Свой эталон — лучшее приближение к эталону организаторов (они размечали по тому же чек-листу; расходиться будем в основном на спорных трактовках), а разметка — первая итерация цикла обучения: каждое решение по спорному месту — правило с причиной (механизм B). Оговорки, принятые в протоколе:

1. **Решает человек.** Чат предлагает метки, Алтай подтверждает или исправляет; метка в эталоне — решение Алтая.
2. **Независимость от пайплайна.** Чату не показываем ответы наших прогонов; желательно модель другого семейства, чем финальная, — иначе точность завышается общими слепыми пятнами.
3. **Отложенная часть.** Адаптацию доказываем только на части эталона, которая не использовалась для настройки (платформа откладывает 40%).
4. **Симулируем проверяющего, а не модель.** Ответы моделей — из реальных прогонов; эталон играет роль решений проверяющего в апелляциях.
5. **Тест адаптивности.** Второй вариант эталона с перевёрнутыми спорными трактовками: система должна сойтись и к нему. Это прямое доказательство тезиса «система подстраивается под проверяющего, а не под наше мнение» и страховка, если реальный эталон трактует спорные места иначе.

Комплект для разметки — [labeling/README.md](labeling/README.md): промпт для чата-помощника с чек-листом дословно, 7 порций диалогов, свод спорных трактовок S1–S12 ([labeling/rulebook.md](labeling/rulebook.md)), формат CSV, совместимый с `gt.import` (проверено на тестовом файле во временном рабочем каталоге).

### Решения

22. **Эталон v0 — разметка Алтая с чатом-помощником на всём DEV** (65 диалогов, 520 меток), `dev-gold@v1`. Пока нет другого эталона, это ground truth для метрик, симуляции апелляций и регрессии. Метки с пометкой `[спорно]` и свод правил хранятся вместе с эталоном.

### 5.2. Codex — честный результат, но выборка слишком мала

- **Маршрутизация:** на готовых прогонах (60 оценок, но только **6 разных диалогов**) сигналы почти не предсказывают ошибку: AUC «бюджет проверки → пойманные ошибки» 0,54–0,61 при случайном 0,5. Лучше других — расхождение моделей (0,60) и низкая `confidence` (0,61), но выбирать по test нельзя. Порог `ambiguities ≥ 6` — кандидат, не правило. `insufficient_data` ещё не было ни в одном ответе.
- **Вывод:** настоящий эксперимент X6 — после R-base (65 диалогов, ответы v2 с `insufficient_data`). Повторить анализ одной командой: `python3 -m variants.codex.sprint1 --out …`.

### 5.3. Antigravity — две проблемы, нужна доработка

1. **Цифры отчёта не совпадают с эталоном.** Отчёт называет их «согласованностью с `dev-gold@v1`», но:

   | Утверждение отчёта | По `dev-gold@v1` на самом деле |
   |---|---|
   | Gemini Flash V1 — 32/32 (100%) | **30/32** |
   | Flash + подвопросы — 31/32 | **29/32** — хуже обычного V1 на этой выборке |
   | `p1-ru-022`: эталон 12.5 | **31.25** |
   | `p1-kz-008`: эталон 40.67 | **38.13** |
   | `p1-ru-012`: в строгом эталоне c07 = «нет» | **N/A в обоих** (R4 этот диалог не менял) |

   Значения в отчёте — по-прежнему ожидания агента, а не наш эталон. Для слайдов их брать нельзя. Корректные цифры даёт `metrics.compare gold=dev-gold@v1 sources=exp_v1:flash,exp_v1:flash_lite,exp_vsubq:subq_flash`.
2. **П30 выполнено наполовину.** Пакеты подвопросов лежат в коде — словарь `STANDARD_SUBQUESTIONS_DATA` с ключами `c01…c08` в `variants/antigravity/subquestions.py`, а в чек-листе их нет. Это не просто стиль: если жюри **изменит формулировку `c07`, сохранив id**, вариант применит старые подвопросы к новому смыслу. Нужно: подвопросы — в версии чек-листа (`checklist.save`, новая версия с полями `sub_questions` / `reduction_rule`), код — только движок; без данных → passthrough.
3. **`runs/r_anti_subq` — по всем признакам синтетические ответы** команды `simulate` (агент `antigravity`, `c01_intro = true` для диалога без имени; 19/40 с эталоном), но лежат в `runs/` как обычный прогон и закоммичены. Пометить в манифесте (`"synthetic": true`) или убрать из `runs/`, чтобы не попали в сравнения.
4. **Экономика:** цены Gemini 1.5 Flash — старые; в `config/pricing.json` у `gemini` цены не заданы.
5. **Хорошее:** пакет `runs/r_subq` — ровно 26 диалогов test, плейсхолдеры правил и прецедентов подставляются; добавлено 2 теста на замену критерия.
