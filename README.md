# Freedom Quality — CQA (Conversation Quality Analytics)

Платформа контроля качества диалогов контакт-центра Freedom Broker, сделанная на хакатоне CQA командой **family-business**. Она оценивает работу оператора в чатах (RU / KZ / EN) и звонках по редактируемому чек-листу:
- ответ по каждому критерию с объяснением и дословными цитатами;
- баллы, которые считает код: веса, перераспределение при N/A, флаг грубой ошибки отдельно;
- апелляции оператора и окончательные решения проверяющих;
- цикл обучения на этих решениях.

**Чем мы отличаемся.** Итоговые баллы у команд будут близкими: все используют разные модели, а точного эталона организаторов не знает никто. Поэтому мы делали ставку на подход, а не на одну удачную настройку. Он держится на трёх опорах:
1. **Исследование** — конфигурации сравнивались на эталоне, и каждое сравнение можно повторить.
2. **Открытая система** — человек управляет каждым этапом.
3. **Замкнутый цикл** — система учится на решениях проверяющих. Этого задание прямо не требовало.

Каждую опору ниже подкрепляют числа.

## Платформа за минуту

```
диалог ──► промпт из активной версии чек-листа (+ уточнения правил и прецеденты, выученные циклом)
      ──► ChatGPT · Codex: новая сессия без контекста (пустая папка, только чтение, без чужих инструкций)
      ──► проверка ответа: схема, допустимые ответы, существование реплик, дословность цитат
      ──► баллы считает код: веса, перераспределение N/A, округление, флаг грубой ошибки отдельно
      ──► карточка: ответ, объяснение, цитаты, уверенность, «Откуда ответ»
      ──► апелляция оператора ──► решение проверяющего (тип A–D, окончательное) ──► итог пересчитывается поверх
      ──► цикл: закономерности ──► предложения оркестратора ──► человек принимает ──► регрессия ──► активация
```

Сайт (`python3 -m cqa serve`, http://127.0.0.1:8765) — корпоративный интерфейс с переключением ролей: администратор, руководитель, проверяющий, оператор. Разделы:

| Раздел | Что в нём |
|---|---|
| **Обзор** | Средний балл, покрытие оценкой, грубые ошибки, открытые апелляции, языки |
| **Диалоги** | Фильтры и вкладки «Оценены / Грубые ошибки / С апелляцией», экспорт CSV |
| **Карточка диалога** | Ответ по каждому критерию с цитатами; клик по номеру реплики — переход к ней; «Откуда ответ»: промпт, сырой ответ, версии; «Оценить диалог» |
| **Очередь проверки** | Ответы, где модель сама сомневается, и апелляции, ждущие решения |
| **Апелляции** | Оператор оспаривает критерий; проверяющий решает с типом A–D; решение можно сделать прецедентом |
| **Операторы** | Статистика по опубликованным оценкам, с размером выборки и без автоматических ярлыков |
| **Чек-лист** | Версии, правка критериев, весов, N/A и шкал; архив вместо удаления; «Активировать и пересчитать» без LLM |
| **Цикл обучения** | Закономерности с уверенностью, анализ оркестратором, предложения, регрессии, «До и после» |
| **Точность** | Любой прогон против эталона: по критериям, с доверительными интервалами и списком расхождений |
| **Оценка и сдача** | Загрузка набора по `group_id`, оценка в фоне с прогрессом, выгрузка и проверка `results` |

## Наш подход

### 1. Исследование: выбор конфигурации подтверждён измерениями

Мы не выбирали модель и схему «на глаз». Около 300 изолированных вызовов LLM сравнивали модели, число подзадач на диалог и способы сведения ответов. Все конфигурации ниже пересчитаны на одном эталоне — нашей разметке всех 65 диалогов DEV ([docs/team/labeling/](docs/team/labeling/README.md)). Это приближение к эталону организаторов, поэтому смотреть стоит прежде всего на разницу между вариантами.

**Модель × декомпозиция.** Одна и та же выборка из 5 диалогов и 40 меток: 4 чата RU / KZ / EN и звонок; у Gemini — 4 чата. Цена — эквивалент API за диалог.

| Модель | Декомпозиция | Вызовов на диалог | $ / диалог | Совпадение меток | Ошибка итога (MAE) |
|---|---|---|---|---|---|
| Claude Haiku 5.5 | V1 — один вызов | 1 | 0,004 | 70,0% | 14,3 |
| Claude Haiku 5.5 | V3 — по вызову на критерий | 8 | 0,011 | 72,5% | 25,6 |
| Claude Sonnet 5.5 | V1 | 1 | 0,052 | 82,5% | 8,6 |
| Claude Sonnet 5.5 | V2 — по секциям | 4 | 0,106 | 82,5% | 14,4 |
| Claude Sonnet 5.5 | V3 | 8 | 0,167 | 82,5% | 12,9 |
| Claude Opus 5.5 | V1 | 1 | 0,107 | **90,0%** | **7,0** |
| Gemini Flash Lite | V1 | 1 | — | 87,5% | 6,3 |
| Gemini Flash | V1 | 1 | — | 93,8% | 5,3 |
| Gemini Flash | подвопросы + сведение кодом | 1 | — | 90,6% | 7,2 |
| **ChatGPT · Codex** | **V1, шаблон v2** | **1** | подписка | 85,0% · **84,4% на всех 65** | 14,8 · **10,6 на всех 65** |

Что из этого следует:
- **Модель важнее декомпозиции.** Переход Haiku → Sonnet даёт +12,5 п. п. совпадения, Sonnet → Opus ещё +7,5 п. п. Дробление на секции или критерии точность не поднимает: у Sonnet 82,5% во всех трёх схемах. Ошибка итога при этом растёт с 8,6 до 12,9–14,4 балла, а цена — в 2–3,2 раза. Отсюда выбор: **один вызов на диалог**.
- **Баллы считает код, а не модель.** Codex сам оценивал итог по каждому из 65 диалогов. В среднем он ошибался на 0,44 балла, но в 2 случаях — больше чем на 5, до 15,4 балла. Код считает итог детерминированно, поэтому LLM отвечает только по критериям.
- **Воспроизводимость.** Два независимых прогона Sonnet V1 совпали в 97,5% решений.
- **Самооценка модели — слабый сигнал.** Уверенность, неоднозначность и нехватка данных, о которых сообщает модель, предсказывают ошибки лишь немного лучше случайного: AUC 0,54–0,61 при случайном 0,5. Поэтому очередь проверки комбинирует сигналы, а последнее слово остаётся за человеком.
- **Выбор — это компромисс, и данные для него сохранены.** Мы не утверждаем, что самый дешёвый вариант лучший. Пример: Opus V1 против Sonnet V1 даёт +7,5 п. п. совпадения за +$0,055 на диалог; на 10 000 диалогов это около $550. Для компании такая цена может быть оправдана, и данные для этого решения есть. На хакатоне мы выбрали Codex через подписку: он не требует отдельного API-ключа и оценивает диалог примерно за 140 секунд, 10 диалогов — за 10 минут.
- **Исследование повторяемо.** В репозитории лежат 16 прогонов с промптами, сырыми ответами и проверками, альтернативные прототипы (`variants/`), эталон и команды сравнения. Появится настоящий эталон — те же сравнения пересчитаются на нём одной командой:

```bash
python3 -m cqa metrics.compare gold=<эталон> sources=sa_v1:sonnet,sa_v1:opus,r-base:codex-cli split=test
python3 -m cqa metrics.before_after gold=<эталон> before=r-base:codex-cli after=r-loop2:codex-cli split=test
```

Выборки на 5 диалогах маленькие, а эталон наш. Полный протокол и все оговорки — в [docs/team/experiments.md](docs/team/experiments.md) и [docs/team/implementation-report.md](docs/team/implementation-report.md).

### 2. Открытая система: LLM — инструмент, решает человек

Решение проверяющего — абсолютная правда (решение 7). LLM и оркестратор готовят черновую оценку, доказательства и предложения, но сами ничего не меняют: ни решений, ни правил, ни весов, ни версий. Каждый этап открыт для управления человеком:

| Этап | Что меняет человек | Как это устроено |
|---|---|---|
| Модель | Провайдер и модель | `config/providers.json`: настроены Codex, Claude Code, Antigravity и ручная вставка; включается одной правкой |
| Промпт | Шаблон, уточнения правил, прецеденты | Шаблоны в `prompts/templates/`; уточнения — версионируемые сущности чек-листа; прецедент — кнопка у решения |
| Чек-лист | Критерии, формулировки, веса, условия N/A, шкалы | 8 неизменяемых версий (v1 — организаторов, v2–v8 — наши); удалённое уходит в архив; пересчёт без LLM |
| Оценка | Ответ по любому критерию | Апелляция → решение с типом A–D и причиной; исходная оценка сохраняется, итог пересчитывается поверх |
| Активация | Какая версия действует | Только человек и только после регрессии на отложенных диалогах |

Прозрачность в цифрах:
- **889 событий** в журнале только с добавлением и цепочкой хешей, проверка `history.verify` — без нарушений;
- **по любой оценке видно**, по каким версиям она сделана: чек-лист, шаблон, параметры, модель, уточнения, прецеденты; «Откуда ответ» показывает точный промпт и сырой ответ;
- **104 команды API** — каждая кнопка сайта; права проверяются по роли, пайплайн и оператор не могут принимать решения;
- **66 тестов**.

### 3. Замкнутый цикл: система учится на апелляциях

Этого не просили прямо, но, по-нашему, в этом смысл контура апелляций. Каждое решение проверяющего попадает в историю и влияет на следующие версии системы — только через человека. Пройденный цикл на DEV:

1. **Решения.** По 39 диалогам части для настройки — 49 апелляций с решениями: тип A — 31, тип B — 18.
2. **Закономерности.** 19 групп «критерий × было → стало × ситуация» прошли порог уверенности: не меньше 3 случаев, 2 разных проверяющих, до 20% противоречий. Ещё 47 копятся: одно решение систему не меняет.
3. **Оркестратор.** Codex за 61 секунду предложил 5 изменений: 2 уточнения правил и 3 прецедента. Ещё он нашёл 2 конфликта: в 15 решениях нашего эталона итог «Да» противоречил обоснованию. Правило из противоречивых данных он выводить отказался и передал вопрос человеку.
4. **Итерация 1.** Без изменений в сумме: исправлено 13 меток, сломано 13. Разбор показал, что правило по c05 сформулировано слишком широко (−15 п. п.).
5. **Итерация 2.** Человек сузил правило — и на 26 диалогах, которые в настройке не участвовали, результат улучшился:

| На 26 отложенных диалогах | До цикла | После двух итераций |
|---|---|---|
| Совпадение меток с эталоном | 84,6% | **88,0%** |
| Ошибка итога (MAE) | 11,5 | **9,6** |
| Итог в пределах ±5 баллов | 31% | **54%** |
| Эмпатия, c05 | 76,9% | 84,6% |
| Ведение диалога, c06 | 73,1% | 92,3% |

Исправлено 10 меток, сломано 3. Выборка маленькая (p = 0,09), но направление ясное. Версия `default@v8` активирована человеком, и контрольный набор оценён уже по ней.

Ещё результаты базового прогона на всех 65 диалогах DEV:
- 879 ссылок на реплики — все существуют, все цитаты дословны;
- грубые ошибки найдены в 8 из 9 случаев, ложных срабатываний нет.

## Быстрый старт

Нужен Python 3.9+, сторонних зависимостей нет.

```bash
python3 -m cqa serve          # интерфейс: http://127.0.0.1:8765 · API: http://127.0.0.1:8765/api/v1/commands
```

- **Оценка моделью.** Используется Codex CLI из приложения ChatGPT — путь задан в [config/providers.json](config/providers.json), вход в ChatGPT должен быть выполнен. Без него работает режим «Вручную»: промпт копируется в любой чат модели, ответ вставляется обратно.
- **Данные организаторов.** Нужен `.env` с `CQA_API_URL`, образец — [.env.example](.env.example). Загрузка — в разделе «Оценка и сдача» или командой `python3 scripts/fetch_dataset.py DEV`.
- **Роль** выбирается внизу бокового меню.

**Контрольный набор за пять шагов:**
1. «Оценка и сдача» → `group_id` → «Загрузить из API».
2. Выбрать набор → «Оценить в фоне» с выгрузкой в `results/prod`.
3. Дождаться статуса «готово» и проверки «пройдена».
4. `git commit`.
5. `git push`.

**Из командной строки** — любая команда API: `python3 -m cqa <команда> ключ=значение`. Фоновое задание `job.evaluate` живёт в процессе сервера, поэтому из командной строки используйте шаги ниже.

```bash
python3 -m cqa run.prepare run_id=r-x dataset=fbroker template=v2 agents=codex-cli   # промпты по активному чек-листу
python3 -m cqa run.dispatch run_id=r-x agent=codex-cli provider=codex-cli          # каждый промпт — новая сессия Codex
python3 -m cqa run.ingest run_id=r-x && python3 -m cqa eval.import source=r-x:codex-cli
python3 -m cqa metrics.compare gold=dev-gold@v1 sources=r-base:codex-cli
python3 -m cqa results.check path=results/prod/results.json set=prod expected=10
python3 -m cqa history.verify
python3 -m unittest discover -s tests                              # 66 тестов
```

## Структура репозитория

```
cqa/                 платформа: пайплайн (prompts, responses, scoring, run), история и состояние (events, state, db),

history/             журнал событий, блобы, задачи оркестратора, отчёты метрик и регрессий
```

## Команда и инструменты

Команда **family-business**. Платформа и эксперименты сделаны вместе с агентами Claude Code, Codex и Antigravity: каждый работал в своей зоне репозитория. Интерфейс — новый сайт команды, подключённый к API платформы.
