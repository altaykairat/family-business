# CQA Hackathon — отчёт, итоги обсуждения и план

> Рабочий документ команды. Исходные материалы: [docs/task.md](docs/task.md) (задание), [docs/checklist.md](docs/checklist.md) (чек-лист), [docs/criteria.md](docs/criteria.md) (критерии отбора), данные — [data/README.md](data/README.md).

## 1. Суть задачи в двух абзацах

Мы строим **Conversation Quality Analytics** для контакт-центра Freedom Broker — автоматизацию работы QA-специалиста. Сейчас человек вручную читает выборку чатов и заполняет чек-лист. Наша система должна делать это для каждого диалога: прочитать транскрипт (RU / KZ / EN, чаты и звонки), выставить оценку оператору по настраиваемому чек-листу, объяснить каждый балл и сослаться на конкретную реплику.

Второй контур — **человек в цикле**: оператор подаёт апелляцию на критерий, проверяющий смотрит доказательства, подтверждает или меняет оценку, система пересчитывает итог и хранит историю. Интерфейс — чистый HTML/CSS/JS, чтобы его можно было встроить в Dynamics 365.

**Главная рамка:** LLM — это быстрый «первый проверяющий», а не судья. Всё остальное (доказательства, апелляции, история, настраиваемый чек-лист) нужно, чтобы его ошибки были видны и исправимы.

## 2. Как нас будут оценивать

### Отбор в топ-50 ([docs/criteria.md](docs/criteria.md))

| Критерий | Вес на практике | Что из этого следует |
|---|---|---|
| **Точность vs Ground Truth** на 10 новых транскриптах | **Главный** | 10 диалогов — очень мало, одна ошибка в критерии заметна. Важна стабильность, а не только «умность». Думать как автор эталона: буквально следовать формулировкам чек-листа |
| Функциональность и уникальные фичи | Средний | Сначала всё обязательное, потом 1–2 «фишки» |
| Удобство | Средний | Каждое действие из демо — в 1–2 клика |
| **Корректность процесса** | Блокирующий | Никаких захардкоженных ответов и критериев в коде. Скорее всего проверят: «поменяйте критерий → перезапустите → результат изменился осмысленно» |
| Разнообразие подходов | Бонус | Хотят сохранить и локальные LLM, и облачные. Шанс выделиться гибридом |

### Защита (5 минут) — фактически приёмочный тест

1. **1 мин** — интерфейс и выбранный диалог.
2. **2 мин** — оценка, обоснование, клик → переход к реплике, пример N/A, итоговый балл.
3. **1 мин** — апелляция → решение проверяющего → новый итог.
4. **1 мин** — изменение критерия в UI → применение чек-листа.

Этот сценарий должен работать безупречно **до** любых улучшений.

## 3. Что мы узнали из данных (DEV)

- **65 диалогов:** 60 синтетических чатов (30 RU, 15 KZ, 15 EN) + 5 реальных звонков (RU). В гайде написано «35 RU» — это чаты + звонки.
- **Структура чата всегда одинакова:** вопрос клиента → бот AIM (приветствие, согласие на обработку данных, ответ) → клиент просит оператора → `system: Эскалация на оператора` → работа оператора → иногда системное событие о завершении.
- **Оцениваем только оператора.** Бот и system — контекст. Приветствие бота не засчитывается оператору.
- **Концовки чатов разные:** «Оператор закрыл чат», «Соединение с клиентом прервано», «Клиент покинул чат» (+ KZ/EN аналоги). Это напрямую влияет на критерий 07 (Нет vs N/A) — похоже, заложено специально.
- **Синтетические чаты, похоже, проверяют каждый свою «ловушку»** по одному критерию.
- **Звонки — сырой ASR**: ошибки распознавания («Пирас… Перрас… Тирас»), дублированные реплики, маскировка `[Имя скрыто]`, `[Персональные данные скрыты]`. Таймстемпы ISO 8601.
- **`audio_url`** ведёт на HTML-страницу плеера, внутри — mp3 в Dynamics с подписью на ~1 час. Для прослушивания и перемотки сервер должен каждый раз доставать свежую ссылку.
- **Ground Truth в DEV нет** — разметку для проверки придётся делать самим.

## 4. Итоги обсуждения

### Договорились (позиция, которую предлагаю принять)

1. **Приоритет:** точность оценщика → стабильное демо → фичи.
2. **LLM определяет ответы, код считает баллы.** Модель возвращает по каждому критерию ответ / ступень шкалы, обоснование и номера реплик-доказательств. Веса, перераспределение N/A, пересчёт шкалы, округление — детерминированный код с юнит-тестами.
3. **Промпт полностью генерируется из чек-листа.** Ни одного упоминания конкретного критерия в коде. Новый / изменённый критерий работает без правок кода.
4. **Схема чек-листа** — [data/checklists/default/v1.json](data/checklists/default/v1.json): секции, типы `binary` / `scale` / `flag`, `weight`, `scale[]`, `na_allowed` + `na_condition`, `global_rules[]`, `scoring`. Грубые ошибки — отдельный тип `flag` (без веса, выводится отдельно).
5. **Общие правила (`global_rules`) редактируются в UI.** Туда же пишем наши трактовки спорных мест — они переживут замену критерия.
6. **Данные в git — только текст:** документы в Markdown, датасет в JSON + MD, PDF игнорируются. Скрипт [scripts/fetch_dataset.py](scripts/fetch_dataset.py) скачивает любой `group_id`.

## 5. Где легче всего потерять точность (спорные трактовки)

Разобрать на реальных диалогах и зафиксировать решение:

- **01 Контакт.** «Поздоровался на языке клиента и представился в первом ответе». Что если клиент в KZ-чате пишет по-русски? «Hi, I'm Leo» — считаем приветствием + представлением (предлагаю: да). Приветствие без имени → Нет.
- **02 Потребность.** Граница Да / N/A. Если данных хватало и оператор сразу ответил — **N/A, а не Нет** (`p1-ru-001`). Модели любят ставить «Нет».
- **03 Идентификация.** Что такое «защищённое действие»? Общий вопрос (тарифы, где найти кнопку) → N/A. Данные конкретного счёта, изменения, вывод средств → нужна проверка.
- **04 Консультация.** Повторил ответ бота, косвенно ответив на вопрос (`p1-ru-012`: «есть ли на русском?» → «предоставляется на английском») — 20 или 15?
- **06 Ведение.** «Явное ожидание» — какая пауза? Задержка до **первого** ответа оператора не считается (порог 3 мин исключён из оценки). Паузы между ответами внутри диалога — считаются, нужно ли было предупредить.
- **07 Завершение.** Главная ловушка. Клиент сказал «всё», оператор не попрощался, потом «Соединение прервано» (`p1-ru-012`) — Нет или N/A? «Оператор закрыл чат» без прощания — по примеру из чек-листа точно **Нет**.
- **08 Грубые ошибки.** Флаг ставится за **само предложение**, даже без согласия клиента. Не дать модели быть «доброй».

## 6. Архитектура (рекомендация)

```
┌──────────────── frontend/ (vanilla HTML/CSS/JS, без сборки) ───────────────┐
│ Список диалогов │ Карточка: транскрипт ⟷ оценка │ Редактор чек-листа │ Апелляции │
└───────────────────────────────┬────────────────────────────────────────────┘
                                │ REST (JSON)
┌──────────────── backend/ (FastAPI, Python) ────────────────────────────────┐
│ dataset: прокси к API организаторов (обход CORS), загрузка по group_id     │
│ checklists: CRUD + версии                                                  │
│ evaluator: препроцессинг → промпт из чек-листа → LLM → валидация → голосование │
│ scoring: детерминированный расчёт (веса, N/A, шкалы, округление, секции)   │
│ appeals: апелляция → решение → пересчёт, история                           │
│ audio: достаёт свежую mp3-ссылку со страницы плеера                         │
│ storage: SQLite                                                            │
└────────────────────────────────────────────────────────────────────────────┘
```

### Оценщик — пайплайн

1. **Препроцессинг.** Нумеруем реплики (`#7 [01:15] operator: …`). Считаем подсказки детерминированно:
   - индекс первой реплики оператора (для 01);
   - язык клиента;
   - паузы между репликой клиента и ответом оператора (для 06);
   - кто и как завершил чат — последнее системное событие (для 07);
   - для звонков — относительное время от начала (для плеера).
2. **Промпт из чек-листа.** Роль QA-эксперта, `global_rules`, для каждого критерия: название, описание, тип, ступени шкалы, условие N/A. Требуем JSON строгой схемы: `{criterion_id, answer, evidence_idx[], explanation, confidence}`. Обоснование — на языке интерфейса (RU), с цитатой реплики.
3. **Валидация.** Ответ из допустимых значений, N/A только где разрешено, `evidence_idx` существуют. При ошибке — повтор.
4. **Стабилизация.** 3 прогона при низкой температуре → голосование большинством по каждому критерию. Сомнительные (расхождение прогонов) помечаем «проверьте вручную» — это же и фича для UI.
5. **Расчёт** в коде (`scoring`), не в LLM.

### Расчёт итога (по чек-листу)

- Да = полный вес, Нет = 0; шкала: `weight × value / max_step`.
- Критерии с N/A исключаются, веса применимых пропорционально масштабируются до 100: `total = Σ points_i / Σ weight_i(applicable) × 100`.
- Округление до 2 знаков. Нет применимых критериев с весом → итог не считается.
- `flag` (грубые ошибки) — отдельной отметкой, на баллы не влияет.
- Итоги по секциям — та же формула внутри секции.

### Фронтенд под Dynamics 365

- Без фреймворков и сборки, относительные пути, один `config.js` с адресом API.
- Компоненты как независимые модули (список, карточка, редактор, апелляции) — каждый можно вынести в отдельный web resource.

### Хранение (SQLite)

`checklists(id, version, json)`, `conversations(id, group_id, json)`, `evaluations(id, conversation_id, checklist_id, version, model, raw_llm, result_json, created_at)`, `appeals(id, evaluation_id, criterion_id, comment, status)`, `decisions(appeal_id, new_answer, reason, decided_at)`.

## 8. Советы и риски

**Советы**
- **Сначала разметка, потом промпт.** Без своих 15–20 размеченных диалогов любые правки промпта — гадание. Размечать по чек-листу двумя людьми независимо, расхождения обсудить — это и есть спорные трактовки.
- **Мерить каждую правку промпта** через `eval.py`, смотреть точность по каждому критерию отдельно.
- **Буквальность важнее здравого смысла.** Лучше вставить формулировки чек-листа в промпт дословно, чем пересказывать.
- **Ловушки — в N/A.** Отдельно проверять, что модель не путает «Нет» и N/A.
- **Не подгонять под DEV.** Никаких правил вида «если conversation_id = …». Few-shot примеры — короткие и синтетические, а не копии DEV-диалогов.
- **Кешировать результаты LLM** по (диалог, версия чек-листа, модель) — экономит деньги и время при итерациях UI.
- **Коммитить часто**, держать `main` всегда рабочим.

**Риски**

| Риск | Митигация |
|---|---|
| Лимиты / недоступность API во время контроля | Прогнать контрольный набор сразу в +23 ч; ретраи с бэкоффом; запасной провайдер |
| Невалидный JSON от модели | Structured output / JSON-схема + валидация + повтор |
| Ссылки на mp3 протухают через час | Всегда доставать свежую со страницы плеера, не кешировать |
| Ссылка API организаторов — подписанная | Держать в `.env`, не в коде |
| Демо ломается вживую | Заранее посчитанные результаты в БД (полученные системой, а не вручную), репетиция, запасное видео |
| Смена критерия на защите ломает промпт | Тестировать заранее: добавить свой критерий, удалить, поменять тип на шкалу |
| Время уходит на UI, а точность не растёт | Владелец оценщика занимается только точностью с 5-го часа |
